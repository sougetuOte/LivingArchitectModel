## 0. 問題

M-1 出口宣言 (b) は「決定木を**新規条項の誕生ゲート**として転用する」と定めたが、そのゲートの出力は 6 値のままであり、6 値はいずれも「既存条項をどう処理するか」の verdict である。新規条項に使うと出力は実質 **二値（収載 / 却下）** に潰れる。

HGA #18 の真の crux: **ゲートの出力が「宛先」の軸を持っていない**。加えて (c) の通貨（規範ストック総量）は、総量建てゆえに (1) 1 対 1 スワップで常駐を永久化し (2) 流入 1 件ごとに削減探しを強制する = **(c) 自身が (a)(b) を破らせる**。

本設計案はこの 1 点（宛先軸 + 通貨改定）を単一の設計コミットとして確定する。

## 1. 決定 D1: ゲート出力を 5 宛先の routing に拡張する

| ID | 宛先 | 実体 | 予算（常駐集合）の消費 |
|:--:|:-----|:-----|:----------------------|
| **R1** | 常駐条項 | `CLAUDE.md` / `.claude/rules/` の `paths:` なしファイル | **消費する** |
| **R2** | 条件付きロード先 | **配送特性の異なる 3 亜種**（v0.4 / 強い順）: **agent 定義**（spawn 時・**compaction 不死**）＞ **skill 本文**（invoke 時・再注入は打ち切りあり）＞ **`paths:` つき rules**（read 時・**compaction で可死**） | しない（§1.2 の要件つき） |
| **R3** | 決定的機構 | hook / test / script | しない（§1.1 の会計つき） |
| **R4** | knowledge 層 | `docs/artifacts/knowledge/` — 記録するが読み込まない | しない |
| **R5** | 却下 | 書かない | — |

**排他ではない**（v0.2 変更 / HGA #19 1-d・5-b）: 軸 3 = 不可逆ガードに限り **R1 + R3 の複宛先を許す**。§1.3 参照。

### 1.1 R3 の会計（v0.2 で実装 / HGA #19 2-c）

v0.1 の「監査面コストを計上する」は単位・列・上限が無い身振りだった。**単位は「機構 1 件 = 恒常監視面 1」とし、R3 台帳に (i) トリガのスキーマ出典 (ii) 判定コマンド (iii) 同時更新義務の有無 の 3 列を記録する**。上限は課さないが、**(iii) が「有」の機構は R3 に置けない**（`rule-002` の same-commit 更新義務が実測済みの恒常税であり、これは散文結合機構の指標そのもの）。これにより「散文をテストに変換して R3 に洗浄する」経路が閉じる。

### 1.2 R2 の形式要件（v0.2 で強化 / HGA #19 2-a）

v0.1 の「どの条件で載るかを 1 行で書ける」は**命名可能性**の検査であり**配送可能性**の検査ではなかった。差し替える。

> **R2 の要件（連言）**: (i) トリガが**ファイル繋留**である（`design.md` §5.2.4 の 3 分類表で「可」= イベント・フェーズ・コマンド繋留は **R2 不可**）∧ (ii) 実際の配送先を明記する（`paths:` glob / skill 名 / agent 名のいずれか）∧ (iii) 軸 3 = 可逆 ∧ **(iv) 失効したときに何が再武装させるかを 1 行で書ける**（v0.4 追加 / 下記）

**イベント・フェーズ・コマンド繋留の条項は R2 に置けない。** §2 の Step 2 でこれらは R1 か R3 に振られる（v0.1 の最大の欠陥。「存在するが二度と読まれない条項」を作っていた）。

#### (i) の適用範囲（v0.4 明文化 / 既定路線の確定）

**(i) は「その R2 項目が自分の発火責任を負う場合」の要件である。** 発火責任を R3 に移譲した項目には適用しない。

この読みがないと §4.1（ゲート自身の配置 = **想起は R3 / 手順本文は R2**）が §1.2 (i) と矛盾して見える。矛盾ではなく**分割パターン**である —— ゲートの想起はイベント繋留だが R3（pytest の集合一致検査）が担い、R2 に置いたのは「呼ばれてから読まれる手順本文」だけなので、(i) の適用対象から外れる。**この分割を採る項目は、想起側の R3 実体を (ii) の配送先と併記すること。**

#### (iv) 再武装条件（v0.4 追加 / 本設計に対する唯一の新規要件）

R2 の 3 亜種は**配送強度が異なり、うち 1 つは失効する**（§1 D1 表の R2 行）。

- **`paths:` つき rules は compaction で失効する**（2026-07-27 の upstream 実測 / `docs/artifacts/instruction-loading-upstream-2026-07-27.md`）。長セッション —— 条件ロードの利得が最も大きい局面 —— でこそ落ちる
- したがって `paths:` に置く項目は、**失効後に何が再び読ませるか**を書けなければ「存在するが二度と読まれない条項」に戻る。v0.1 の最大の欠陥が、繋留の分類を通過した項目の内側で再発する

**v5.0.0 の R2 降格 2 件が生きている理由を、この要件で説明できる**（事後の追認ではなく判定基準として機能することの確認）:

| 降格した項目 | 再武装させるもの |
|:---|:---|
| `model-delegation-prompting.md` | **不死チャネルへ逃がした** —— 受領側に効く 5 条項を `.claude/agents/*.md` の §受領側の恒久制約に常駐化済（agent 定義 = spawn 時配送・compaction 不死） |
| `planning-quality-guideline.md` | **アンカーが自己再武装する** —— `docs/specs/**` を触れば必ず再ロードされる。PLANNING の成果物はそこにしか置けない |

**逆に、いずれも書けない項目は R2 に置かない。** R1 に残すか R3 へ移すか R5（却下）とする。

> **本節の予算**（WC-16「配送台帳の第二憲法化」への防御 / `CHANGELOG.md` §決定 5）: 配送チャネルの区別に対する条文化は **§1.2 の要件 1 本（= (iv)）と宛先表の 1 行（= §1 D1 の R2 行）を上限**とする。上記「(i) の適用範囲」は**新規要件ではなく既存要件の適用範囲の明文化**であるため予算外とする。**分類学・メタデータ列・検査群へ育てないこと。** (iv) の検査は人手の 1 行記述であり、機構を伴わない（伴わせれば R3 の会計 §1.1 (iii) に抵触する）。

### 1.3 不可逆ガードの二重化（v0.2 新設 / HGA #19 5-b への回答）

HGA #18 の結論は「禁止型こそ最も価値がありかつ最も decay する」であり、v0.1 は「禁止型は R1 に残る」と読み替えて decay 対処を落としていた。**R1 に置く禁止型は、機構化可能なら R3 と二重化することを必須とする**（`git push --force` の 散文 + deny の現行形が先例）。機構は settings drift で沈黙し得るが、二重化があれば沈黙を知る規範が残る。

## 2. 決定 D2: 宛先の判定順序（先頭一致 / 決定的）

既存 4 軸 + 基質適合テスト + 条件ロード判定を**流用**する。**新しい軸は追加しない。**

```
[Step 1: 機構テスト] → R3
  次の 3 条件をすべて満たすか:
    (a) 機構が検査する【入力にスキーマ契約がある】（v0.2 修正: 旧「トリガが構造化イベント」）
    (b) exit-code 級の機械判定で合否が出る
    (c) 意味解釈が不要
  すべて YES → R3（+ 軸 3 不可逆なら R1 と二重化 = §1.3）
  1 つでも NO → 機構化しない → Step 2 へ

[Step 2: 到達必要性テスト] → R1 / R2
  軸 3 = 不可逆ガード                   → R1（条件ロードは構造的に間に合わない / §5.2.4 (B)）
  繋留先が【ファイル】 かつ 軸 3 = 可逆  → R2（§1.2 の 3 要件を満たすこと）
  繋留先が【イベント / フェーズ / コマンド】→ Step 3 へ（R2 は選べない）

[Step 3: 基質適合テスト] → R5
  「Opus 5 は指示なしでこれをやるか」= YES → R5（却下 / 書かない）
  NO → Step 4 へ

[Step 4: 軸 4（根拠）] → R4 / R1（形式は Step 5 で決める）
  検出イベント 0 件 → R4（knowledge 層に記録して待つ / 再入場は §4.3）
  検出イベント ≥ 1 → Step 5 へ
     ※ v0.2 修正: 旧「< 2 → R4」は design.md §5.2 軸 4（≥ 1 = 実測由来）と不整合だった。
       既存条項の残留基準と新規条項の入場基準を一致させる（HGA #19 1-e）。
       trust-model.md の閾値 2 は「rule 候補の提案」の閾値であり常駐入場の閾値ではない。

[Step 5: 形式（v0.2 新設 / 6 値の像を回復 / HGA #19 1-c）]
  帰属がモデル固有の事実 → R1 かつ【SSOT 退避】= model-roster.md へ（新規ファイルを作らない）
  軸 2 = 列挙            → R1 かつ【圧縮】= 意図 1 行に畳み、根拠は docs/artifacts へ
  軸 2 = 意図            → R1 かつ【保全】= 原文のまま
```

**Step 5 の位置づけ**: R1 は「宛先」、圧縮 / SSOT 退避 / 保全は「**その宛先での形式**」。v0.1 は 6 値を 5 宛先に射影して 2 verdict（圧縮・SSOT 退避）を失っていた。宛先と形式を直交させることで復元する（`design.md` §5.2 が「判定軸とロード条件は直交する配置属性」としたのと同じ構造）。

R1 に残るのは「**不可逆ガード**」または「**ファイル繋留でない × 基質が代替しない × 実測 1 件以上**」の交差のみ。

## 3. 決定 D3: 通貨を「常駐集合」建てに改定する

### 3.1 定義（v0.2 で単位を凍結 / HGA #19 2-b・5-a）

> **常駐集合 = R1 台帳に列挙された条項の集合**。予算の単位は **台帳 1 行 = 1 条項**。

- v0.1 の「条項数」は判定者の裁量に単位を委ねており、**3 条項を 1 見出しに融合すれば count が 2 減る**という粒度ゲームを支配戦略にしていた（HGA #19 2-b）。単位を台帳行に凍結し、条項 ID 体系（M-1 実装済み / `<file>#<section>-<nn>` 形式）を正本とする
- **統合・分割は「行の変換取引」として台帳上で数を保存する**（3 行を 1 行に融合するなら、台帳上も 3 行のまま `merged-into:` を記録する）。判定者間の安定（仮定 4）を「判定」ではなく「台帳照合」に置き換える
- 行数・フォーマットは単位にしない（markdown / plain / table の差 2.1pp 未満 / ファイルサイズ 25-500 行は帰無を積極支持 BF 0.05-0.10）

**実装時に判明した役割分離**（v0.3 追記 / 台帳 §A・§B）: 「台帳行 = 単位」を実装したところ、**1 つの表では両立しない 2 つの役割**が現れた。

| 役割 | 実体 | 検査 |
|:-----|:-----|:-----|
| **天井ゲージ**（80 との対比 / 常駐面の混雑度） | 台帳 **§A** = ファイル別の指令出現数 | **pytest で機械検査** |
| **通貨**（no-net-growth の 1 対 1 / net-negative の 1 対 2） | 台帳 **§B** = 1 行 1 条項の取引簿 | 人手（判断の記録 / 機械判定不能） |

**§A は通貨ではない。** 2026-07-26 の初回取引で実測された非対称がこの分離の根拠である —— `fable-l3-protocol.md` の退出は §A を 19→18 に動かしたが、`phase-rules.md` の退出は **12→12 で動かなかった**（削除した箇条書きが RFC 2119 キーワードを含まないため）。**§A が動かない条項の出入りがある**ため、§A を通貨にすると「§A に現れない条項」が無制限に入れる。

**#18 の「同時指示数」との差**（v0.2 で明示 / HGA #19 5-a）: #18 の文言は「同時**指示**数」であり、本設計の「台帳行」は**その代理変数**である。LAM 条項 1 行が研究上の指示 1 に対応する保証はない（**換算は未測定 = §6 仮定 2**）。代理変数を採る理由は、指示数を直接数える手段が存在せず、台帳行だけが操作されにくい観測量であること。**この置換は宣言のうえで行う**。

### 3.2 no-net-growth（相対規律）

> **R1 台帳に 1 行を追加する = R1 台帳から 1 行を退出させる**（退出先は 削減 / R2 降格 / R4 退避）。

**R2 → R1 昇格の予算意味論**（v0.2 新設 / HGA #19 2-a(ii)）: **昇格は予算を消費する**（= 交換相手を要する）。ただし**昇格が §1.2 の要件違反（R2 誤配）の是正である場合に限り、交換相手を「誤配した本人の他の R1 行」から取らず、退出義務を免除する**。理由は非対称にある —— 是正に予算を課すと是正が抑止され、無料にすると「まず R2 に置いて後で無料昇格」というバイパスが開く。**誤配の是正だけを無料にする**ことで、バイパスの利得は「誤配を自認する」というコストと引き換えになる。

**交換相手の制約**（v0.2 新設 / HGA #19 3-d）: 退出させる行は「**別途の理由で既に削除が決まっている条項であってはならない**」。どのみち死ぬ条項を交換相手に使う退出は実質オフセットゼロであり、count 通貨下では**死に条項の備蓄**が合理的行動になる。

### 3.3 絶対上限は 1 点のみ

- **hard ceiling = 80**。N=80 で perfect-response rate が全モデル・全フォーマット・両配置でゼロ（arXiv:2607.19257）
- **これを外部定数として扱うが、物理定数として扱わない**（v0.2 修正 / HGA #19 5-c）: HGA #18 が確信度 70% の最大要因とした「単発 eval 知見の統治コーパスへの転移未検証」は、この数字にも等しく適用される。80 は**現時点で参照できる唯一の実測境界**であり、Opus 5 での再現も台帳行への換算も未検証（§6 仮定 1・2）
- **運用目標値（40 等）は定めない**。40 は Sonnet 5 / Haiku の数字であり、目標値を決めると「守るための計測機構」が生まれ機構が監査面を増やす

### 3.4 測定は 1 回だけ

- ゲート発効時に R1 の条項を**列挙して台帳を作る**（ベースライン）。**各条項の verdict は再判定しない**（§0.1）
- 以後は差分管理（追加 / 退出で ±1）。**再カウントの定期棚卸しは行わない**（(a)(b) と整合）
- 現在値は台帳の **status 列が `resident` の行数**で得る（v0.2 修正 / HGA #19 2-d: append-only 台帳では退出も追記されるため、単一パターンの `grep -c` では現在値が出ない）

### 3.5 ベースラインが天井を超えて生まれた場合（v0.2 新設 / HGA #19 WC-2）

**L1 実測（§0.2 #5）により、これは想定ケースではなく既定の前提である。** どの単位を採ってもベースラインは 80 に触るか超える。

v0.1 にはこの規定がなく、HGA #19 の指摘どおり **是正の合法手段が憲法上存在しなかった**（(a) が consolidation Milestone を禁じ、転落条件 ② が再採点を禁じ、no-net-growth は現状維持しかしない）。解を**フロー側の交換レートだけ**に置く:

> **R1 台帳の `resident` 行数が 80 を超えている間、交換レートを net-negative（1 行追加 = **2 行退出**）に切り替える。80 以下に戻ったら 1 対 1 に復帰する。**

- **(a) を破らない**: Milestone を立てず、定期棚卸しもしない。減るのは**新規流入が起きた時だけ**
- **転落条件 ② を破らない**: 退出は「新条項の入場と引き換えに 2 行を選ぶ」判断であり、既存条項の**網羅的な再採点ではない**
- **成功指標にしない**（転落条件 ④）: 「何行減らしたか」は評価軸にしない。減少は流入の副産物である
- **流入が止まれば減少も止まる**。これは欠陥ではなく仕様である —— 流入がないなら常駐の負荷は現状のまま許容されている、というのが (a) の宣言内容そのもの

## 4. 決定 D4: ゲート自身の配置（自己適用）

### 4.1 判定

| Step | v0.1 の判定 | v0.2 の判定（HGA #19 3-c） |
|:-----|:------------|:---------------------------|
| Step 1（機構） | 「新条項を追加しようとしている」は構造化イベントでない → R3 不可 | **藁人形だった**。実装可能なトリガは「**Edit / Write の対象パスが `.claude/rules/**` 等に一致**」であり、(a) 入力（パス文字列）にスキーマ契約あり (b) パス一致の機械判定 (c) 意味解釈不要 = **Step 1 を全通過する** |
| Step 2 | 契機は PM 級編集の事前宣言義務（散文） | **不採用**（§4.2） |

**結論: ゲートの想起は R3（決定的機構）に置く。手順本文は R2（skill）に置く。**

### 4.2 散文の契機を捨てた理由（HGA #19 3-a・3-b）

v0.1 が採った「PM 級編集の事前宣言義務に語句を足す」は、**主要 3 経路を素通しにする**。

| 経路 | 素通しの理由 | 出典 |
|:-----|:-------------|:-----|
| 委譲経路 | `core-identity.md` が「**subagent 経由の編集は宣言不要**」と明記。かつ憲法は「3 ファイル以上の文書補追は L2」「迷ったら委譲側に寄せる」 → **ゲートの唯一の契機が、憲法が避けよと言う経路にだけ立つ** | `core-identity.md` §不要なケース / `CLAUDE.md` §担当層 |
| セッションスコープ降格 | 同一セッション 2 回目以降の同一ファイル編集は宣言不要。**条項流入は別作業の最中に起きる**（`rule-002` が M-1 W0 作業中に誕生した実測）= まさに降格が効いている時間帯 | `permission-levels.md` §セッションスコープ / `retro-M1` 記録 5 |
| `CLAUDE.md` 経路 | `CLAUDE.md` は PM 級パス表にも hook の `_PM_PATH_REASONS` にも**不在**（L1 実測）。**最も常駐する 1 ファイルへの条項追加が PM ダイアログも宣言義務も経ない** | §0.2 #3 |

hook はパスで発火するため、**編集主体（L1 / subagent）とセッション内回数を問わない**。3 経路すべてが同時に塞がる。

### 4.3 実体（v0.3 で主従を入替 / 仮定 6 の実測結果）

**L1 実測（2026-07-26 / upstream-first）**: `additionalContext` は PreToolUse の公式フィールドであることを context7 で確認したが、**公式例は `permissionDecision: "allow"` との組み合わせ**であり、LAM 自身のコード注記（`pre-tool-use.py:402-403` / ADR-0008 Phase B-2c 実装時の裏取り）は「**system reminder ラップで tool result の隣に挿入される**」と述べている。すなわち **`ask` 経路の `additionalContext` は編集の後に届き、事前ゲートになれない**（事後通知にしかならない）。

したがって v0.2 §4.3 が `additionalContext` を主契機に置いた構成は成立しない。**HGA #19 が仮定 5 の代替骨格として挙げた「出口の不動点で拾う」を主に、`additionalContext` を従に入れ替える。**

| # | 実体 | 内容 | 予算 |
|:-:|:-----|:-----|:-----|
| 1 | **`.claude/tests/` に集合一致検査を新設（主契機）** | **R1 台帳の条項 ID 集合** と **常駐ファイル内の ID アンカー集合**の一致を pytest で検査する。ゲート未通過の条項追加は**テストが落ちる**ことで発覚する。ID 照合は意味解釈を要さないため `rule-001` 型の regex 追跡病理に当たらない（§1.1 の (iii) 同時更新義務 = **無**: 台帳と常駐ファイルは同一 commit で動くのが正常であり、外部の漂流入力を追わない） | **R3**（消費なし） |

**#2 を未実装とした判断（2026-07-26 / 実装時）**: #1 が Green で動いた時点で #2 の追加価値は「事後想起の二重化」に留まる一方、実装は **全 PM 級パスが通る共有の permission response 経路**（`_emit_permission_response`）に手を入れることになる。承認ゲートの中心経路をゲートの補助機能のために変更するのは、得られる利得（想起の二重化）に対して爆風半径が大きい。**保留とし、#1 の潜伏（§8）が実害として観測された時点で再検討する**（検出イベント 1 件目で台帳 §D に載る）。

**主契機が #1 になったことの含意**: ゲートは「編集の直前に思い出させる機構」ではなく「**編集後に台帳と食い違っていたら落ちる機構**」になる。これは M-1 Keep 2 の結論（**自己検証は内側でしか働かず、外部との突合は機構でしか担保できない**）の直接適用であり、§4.2 の 3 経路（委譲 / セッション降格 / `CLAUDE.md`）すべてを**編集主体を問わずに**塞ぐ点で `additionalContext` より強い。代償は「違反が commit 前の test 実行まで潜伏する」ことだが、規範編集は軸 3 で可逆側であり損害は有界である。

**R4 在庫を同一ファイルに置く理由**（v0.2 新設 / HGA #19 追加指摘 1）: R4 の「2 件目で再入場」は、再入場の契機がなければ一方通行になる。台帳を同一ファイルにすれば、**ゲートを通すたびに R4 在庫が目に入る**。契機は既に構造化トリガ化済み（#1）であり、追加機構ゼロ。

## 8. 残る弱点（設計として認める）

- **WC-1（R2 沈殿池）は完全には塞がっていない。** 配送可能性要件はファイル繋留の判定を強制するが、「glob が実際にマッチする頻度」は判定時に検証できない。禁止型の違反は omission であり静かに潜伏するため、誤配の発見は依然として遅い。**§3.2 の昇格無料化はこの遅さを前提とした緩和策であり、解決ではない**
- **仮定 6 は決着したが、決着の中身は「主契機を差し替えろ」だった。** `additionalContext` は編集後に届くため事前ゲートになれず、主契機は pytest の集合一致検査（§4.3 #1）に移った。残る弱点は**潜伏時間** —— ゲート未通過の条項追加は「次に pytest が回るまで」検出されない。commit 前に必ず回る運用（`/ship` Phase 3）に依存しており、**pytest を回さずに push する経路では潜伏が延びる**
- **主契機が事後検出になったことで、ゲートは「追加を止める機構」ではなく「追加と台帳の不一致を落とす機構」になった。** 条項が routing を経ずに R1 に入り、あとから台帳に追記されて整合する（= 判定を通さずに帳簿だけ合わせる）経路は塞げていない。これを塞ぐには台帳行に判定根拠列を要求するしかなく、**根拠列の中身が正しいかは機械判定できない**
- **§3.5 の net-negative は流入が止まれば減少も止まる。** これは (a) の宣言内容と整合する仕様だが、「天井超過状態が長期に残る」ことを許す
