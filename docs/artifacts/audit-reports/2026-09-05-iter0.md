## Critical

### C-1 `py_invoke.sh` の allowlist が `-c` 任意コード実行を許し、Bash deny リストを全て迂回する【PM】

- 場所: `.claude/settings.json:32` `"Bash(bash .claude/scripts/py_invoke.sh *)"` / `.claude/scripts/py_invoke.sh:41` `exec "$PY" "$@"`
- 症状: 末尾ワイルドカードが `py_invoke.sh` の**任意の引数**にマッチするため、`bash .claude/scripts/py_invoke.sh -c "<任意 Python>"` が無承認で通る。Python は `os.system` / `subprocess` / `shutil` で `rm -rf` 相当・`chmod`・`git push --force` 相当を全て代替できるため、`.claude/settings.json:34-58` の deny リスト（`rm` / `mv` / `chmod` / `chown` / `git push --force` / `git reset --hard` …）は**この経路からは一切当たらない**。
- **L1 実測**: 本監査セッション自身が `py_invoke.sh -c "<複数行 Python>"` を**承認ダイアログなしで 6 回実行**した（Stage 1 の `run_phase0` 実行 / チャンク生成 / hook 判定関数の直接呼び出し等）。攻撃を実演する必要すらなく、**通常運用がそのまま実証になっている**。
- 帰責: upstream（`security-commands.md` §D4「allowlist prefix 1 本」の設計が、`-c` を持つインタプリタラッパーには適用できない）
- 提案: `.claude/settings.json` の当該 allow を `Bash(bash .claude/scripts/py_invoke.sh *.py)` 相当へ絞る、**または** `py_invoke.sh` 側で `-c` を拒否する自己防御を入れる。後者なら `settings.json` に触れずに閉じられる。
- **注意**: `settings.json` は AI 編集不可。**提案のみ**。
