## §1 計器の較正（測定に先立って判明した 2 つのずれ）

| # | 記録上の表記 | 実体 | 倍率・差分 |
|:-:|:---|:---|:---|
| **1** | 「137,537 **文字**」 | **UTF-8 バイト数** | 実文字数 80,263 に対し **1.75 倍** |
| **2** | そのバイト数 | **作業ツリーの `wc -c`（CRLF 込み）** | git blob（LF）比 **+1,697 バイト** |

### 較正の根拠

`8fc40f07`（前回の記録時点）の git blob 実測 = **135,848** バイト。当時の R1 行数 2,312 のうち CRLF 行が 1,689 → `135,848 + 1,689 = 137,537` で**記録値と完全一致**。同様に現在は `138,540 + 1,697 = 140,237` で記録値と一致する。したがって、これまでの全記録は**作業ツリーの CRLF バイト**を「文字」と呼んできたことが確定した。

### なぜこのずれが実害を持つか

質量削減の判定が**計器依存**になる。日本語 1 文字 = 3 バイト、ASCII 1 文字 = 1 バイトであるため:

- **バイトで測る** → 日本語の散文を削り ASCII（パス・識別子・表の罫線・コード片）を増やす編集は**大きく減って見える**
- **文字で測る** → 同じ編集はほとんど減らない
- **`\r` を含める** → 行を増やすだけで質量が増え、行を減らすだけで減る（内容と無関係な成分が約 1.2% 混入）

本レポートは以下すべて **git blob（LF 正規化）の UTF-8 バイト**で統一する。

## §2 測定方法

### R1 の集合定義（台帳 §A / `test_clause_gate_ledger.py` と同一）

ルート `CLAUDE.md` + `.claude/rules/**/*.md` のうち、**先頭 3 行に `paths:` を持たないもの** = 無条件ロード。

本レポートはこれに加え、`paths:` の有無を問わない**同一ファイル集合の総量**（以下「**総量**」= R1 + R2）を並行して測る。降格（reclassification）と削除（deletion）を分離するため。

### 履歴の再構成

各 commit で `git ls-tree -r` からファイル一覧と blob hash を取り、その時点の内容で `paths:` 判定と計数をやり直す。**過去の各時点にその時点の定義を適用する**（現在の定義を遡及適用しない）。blob hash でキャッシュするため git 呼び出しは実質差分ぶんのみ。

### 再現スクリプト

```python
"""R1 と「R1+R2 の総量」を同時に追う。降格が『削減』かどうかを分離するため。"""
import re, subprocess

REPO = "D:/work7/LivingArchitectModel"
DIRECTIVE_RE = re.compile(r"MUST NOT|MUST|SHOULD NOT|SHOULD|禁止|必須|してはならない")

def git(*a):
    return subprocess.run(["git", *a], cwd=REPO, capture_output=True, text=True,
                          encoding="utf-8", errors="replace", check=True).stdout

def git_bytes(*a):
    return subprocess.run(["git", *a], cwd=REPO, capture_output=True, check=True).stdout

def is_target(p):
    return p == "CLAUDE.md" or (p.startswith(".claude/rules/") and p.endswith(".md"))

_c = {}
def measure(blob):
    if blob not in _c:
        norm = git_bytes("cat-file", "blob", blob).decode("utf-8", "replace").replace("\r\n", "\n")
        resident = not any(l.startswith("paths:") for l in norm.split("\n")[:3])
        _c[blob] = (len(norm.encode("utf-8")), len(DIRECTIVE_RE.findall(norm)), resident)
    return _c[blob]

commits = [l.split("\x1f") for l in git(
    "log", "--reverse", "--format=%H\x1f%ad\x1f%s", "--date=short",
    "--", "CLAUDE.md", ".claude/rules/").strip().split("\n")]

for sha, date, subj in commits:
    r1b = r1d = r1n = allb = alld = alln = 0
    for line in git("ls-tree", "-r", sha).strip().split("\n"):
        meta, path = line.split("\t", 1)
        if not is_target(path):
            continue
        _, otype, blob = meta.split()
        if otype != "blob":
            continue
        b, d, resident = measure(blob)
        alln, allb, alld = alln + 1, allb + b, alld + d
        if resident:
            r1n, r1b, r1d = r1n + 1, r1b + b, r1d + d
    print(date, sha[:8], r1n, r1b, r1d, "|", alln, allb, alld, "|", subj[:44])
```

> **実行時の注意**: Windows の cp932 ロケールでは commit subject の em dash 等で `UnicodeEncodeError` になる。`PYTHONIOENCODING=utf-8` を付けて起動すること（`.claude/rules/subprocess-encoding-convention.md` の趣旨を stdout 側にも適用する）。

## §5 発見 A — R1 の減少は、総量の減少ではない

**R1 ピーク（167,903）から R1 の底（131,566）まで −36,337 バイト。同区間の総量は 167,903 → 167,921 で +18 バイト。**

減った 36,337 バイトを分解すると（区間内 7 commits の総和）:

| 内訳 | バイト |
|:---|---:|
| **R2 への降格**（`paths:` 付与 / ファイルは同じ場所に残存） | **−36,355** |
| 実削除（総量が減った commit の合計 / `639a2969` `1aa50a9b` `7f2febb5` `5d0b7cf8`） | −6,606 |
| 同期間の新規追加（総量が増えた commit の合計 / `2339b1a9` `f332a30d` `44f62e2c`） | **+6,624** |
| **ΔR1 合計** | **−36,337** |
| **うち正味の総量変化**（降格を除く） | **+18** |

**実削除 6,606 バイトは、同じ区間の新規追加 6,624 バイトにちょうど相殺されている。** 削減キャンペーンの正味の成果は **+18 バイト（増加）** であり、R1 の見かけ上の −36,337 は**全額が降格**である。

降格した 5 ファイルは**すべて `.claude/rules/` 配下に現存**しており（§3 の R2 表 / 計 36,659 バイト）、削除も移動もされていない。差分は `paths:` フロントマターの 1 行のみである。

### この降格は配送コストすら減らしていない

2026-07-27 の currency sweep（`docs/artifacts/instruction-loading-upstream-2026-07-27.md`）が確定させた upstream 実測により、**`paths:` 降格は compaction で失効する**。すなわち長セッション——質量が効く唯一の局面——では 36KB が context に戻る。

**本レポート執筆セッション自体が実例である**: Python テストファイルを Read した時点で `subprocess-encoding-convention.md`（9,969 バイト / R2）が system-reminder として context に注入された。R2 は「読まれない」ではなく「**契機が来たら読まれる**」であり、契機は日常的に来る。

これは HGA #24 の「**R1 は純粋なコストではなく最上級の配送チャネル**であり、カウント通貨は最良チャネルからの退避を過大報酬してきた」と正確に一致する。**R1 の数字が下がったのは、質量が減ったからではなく、計器が数えるのをやめたから**である。

## §9 この測定が示さないこと（限界）

- **意味的な冗長性を測っていない**。バイト・文字・指令数はすべて構文的な計器であり、「同じことを 2 か所で言っている」は検出できない（それが手 4 の矛盾統制の領分）
- **配送の実測ではない**。実際に context に載るバイト数は compaction・skill description・subagent 継承の影響を受ける。本測定はリポジトリ上の静的な質量のみ
- **R2 の契機頻度を測っていない**。「compaction で失効する」は upstream 実測だが、実運用で何割のセッションが該当するかは未測定
- **`.claude/rules/` と `CLAUDE.md` の外を見ていない**。skills / agents / hooks の記述量は対象外
- **除去の難易度を測っていない**。20,324 バイトの `hga-summoning.md` が 1,650 バイトの `README.md` より削りやすいとは限らない

## §10 帰結と、次の判断材料

1. **計器のラベルを直す必要がある**（下記 §11 の申し送り）。「文字」と書いてバイトを測り、そこに CRLF が混入している状態では、削減の成否を議論できない
2. **降格を「削減」として計上しない計器が要る**。総量（R1+R2）を並記すれば、降格と削除は自動的に分離される。本レポート §2 のスクリプトがその最小実装である
3. **`HARD_CEILING = 80` に張り付いている**。天井は現在、増加を止める唯一の機構として機能しているが、**降格という抜け道が開いたまま**である（指令 23 件が実際にそこを通った）
4. **手 4 の判定材料**: 手 4 の後に本測定を再実行し、**総量**が減っていれば §10 の診断は正診、R1 だけが減って総量が横ばいなら再び降格が起きたことになる
