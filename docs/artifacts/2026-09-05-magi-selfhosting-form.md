## 発端 —— 実測が先行決定の前提を崩した

配布形態 MAGI（`2026-09-04-magi-distribution-form.md` §A3）は
「**self-hosting は維持。ただし同居から『同一リポジトリ内 plugin の local install』へ形を変える**」と結論した。
BALTHASAR はそのとき条件を付けていた ——「**plugin の local install が同一実体を指せるかが分かれ目**」。**それが未検証のまま残っていた。**

2026-09-05 に lam-p1（捨てプロジェクト）で実測した:

| 観測 | 値 |
|:--|:--|
| marketplace `installLocation` | `D:\work7\LivingArchitectModel`（コピーなし） |
| plugin 本体の実体 | `~/.claude/plugins/cache/lam/lam-harness/**0.1.0**/` に **787K のコピー** |
| コピー元 | **git ではなくワークツリー**（未コミットの agents 12 件まで含まれた） |
| ソースを編集 → `/reload-plugins` | **キャッシュは install 時点のまま**。変更は届かない |

上流ドキュメント（`plugin-marketplaces`）が理由を明示している ——
**バージョンがキャッシュパスと更新判定を決め、解決したバージョンが既存と一致すると update はスキップされる。
`plugin.json` に明示バージョンがあると、文字列を上げるまで固定される。git ソースでバージョン未指定の場合のみ commit SHA が使われる。**

**したがって A3 の「local install = 同一実体」は上流実装により成立しない。** 本 MAGI はその訂正である。

## Atom A1: 日常セッションの供給経路

**[MELCHIOR]**: `--plugin-dir` が唯一の live 経路である。編集が即座に効き、self-hosting が本来求める
「自分の最新のハーネスを自分で踏む」が成立する。install はキャッシュを挟むため、LAM は**自分が今書いている
ハーネスではなく、いつか install した過去のハーネスを踏む**ことになる。それは QA 機構としての self-hosting が
死んでいる状態だ。速度面でも version bump も push も要らず最速。

**[BALTHASAR]**: 3 つ穴がある。

1. **起動オプション依存 = 忘れたら無防備**。P4 で project hooks を撤去した後、`--plugin-dir` を付け忘れた
   セッションは**ガードがゼロで立ち上がる**。しかもそれは静かに進行する（承認ダイアログが出ないだけで
   エラーは出ない）。LAM が最も嫌う無音の失敗そのものだ。
2. **利用者が踏む経路と違う**。利用者は install 経由で入る。上流は `--plugin-dir` を
   「インストールせずにテストするため」と明記している。**self-hosting の目的は「利用者と同じ経路を踏むこと」**
   であって「最新を使うこと」ではない。MELCHIOR はこの 2 つを混同している。
3. **I-2 の射程外に出る**。ADR-0010 は「enable はプロジェクト設定スコープでのみ」と定める。
   `--plugin-dir` は設定ファイルに現れず、**構成が起動コマンドの記憶に依存する**。

**[MELCHIOR]**: しかし install だけでは編集が自分に届かない。LAM の開発サイクルは
「plugin を直す → 自分で使って壊れ方を見る」だ。届かなければ self-hosting は形骸になる。

### Debate

両者が指しているのは**異なる 2 つの目的**であり、1 つの経路では両立しない。

| 目的 | 満たす経路 |
|:--|:--|
| **(i) 編集中の実体を自分で踏む**（開発中の変更が効く） | `--plugin-dir` のみ |
| **(ii) 利用者と同じ配布経路を踏む**（配布形態そのものの検証） | install のみ |

A3（配布形態 MAGI）が「self-hosting」と呼んでいたものは (ii) であり、BALTHASAR が HGA #22 を引いて
「唯一の QA 機構」と言ったのも (ii) である。一方 MELCHIOR が守ろうとしているのは (i) である。
**両方要る。片方を選ぶ問題ではない。**

**[CASPAR]**: 結論: **併用（案 D）。ただし役割を明示的に分ける。**

- **既定は install（project スコープ）** —— I-2 に準拠し、設定ファイルに現れ、**忘れても効く**。
  利用者と同じ経路であり (ii) を満たす
- **plugin を編集した直後の検証だけ `--plugin-dir` セッションを明示的に立てる** —— (i) を満たす。
  上流も「同名の marketplace plugin を上書きする」と明記しており、**構造としては上流の想定どおり**
- 既定を install に置くことで、BALTHASAR の穴 1（忘れたら無防備）が消える。
  `--plugin-dir` は**意図的な行為**になり、忘れても既定へ落ちるだけになる

**採用しなかった選択肢とその理由**:
- **A（`--plugin-dir` 常用）**: 穴 1 が残る。ガードの有無が起動コマンドの記憶に依存する構成は、
  LAM が hooks に求めてきた「静かに死なない」と正面から反する
- **B（install のみ + 都度 version bump）**: (i) を version 文字列で買うことになり、
  **バージョン番号が「編集回数」に化ける**（A2 で棄却）
- **C（github + version 撤去）**: push しないと自分で試せない。(i) が push レイテンシに縛られる

## Atom A2: `plugin.json` の `version` を保持するか

**[MELCHIOR]**: 撤去すれば github source で commit SHA 駆動になり、push のたびに更新が届く。
version bump という人手の儀式が消える。人手の儀式は必ず忘れられる。

**[BALTHASAR]**: 撤去すると**利用者側も SHA 駆動になる**。plugin は安定版を配るものであり、
利用者が意図せず開発中の HEAD を掴む構成は配布物として危険だ。
`/plugin update` の粒度が「コミット」になり、利用者に「どの版を使っているか」を説明できなくなる。
LAM には 31 リリースのタグ運用があり、それと矛盾する。

**[CASPAR]**: 結論: **`version` は保持する。ただし bump を `/release` に紐付け、開発ループには使わない。**

A1 で (i) を `--plugin-dir` が担うことになったため、**version bump を開発中の反映手段に使う必要が消えた**。
bump はリリース時の 1 回だけになり、MELCHIOR が懸念した「忘れられる儀式」ではなく
「リリース手順の一部」になる。

**採用しなかった選択肢**: version 撤去 → 利用者が HEAD を掴む / リリース番号が説明不能になる。

---

## Atom A3: marketplace source（`directory` か `github` か）

**[MELCHIOR]**: `directory` のままなら push 不要で install でき、ローカルでの試行が速い。
実際、今日の測定は `directory` で行えた。

**[BALTHASAR]**: **追補 1（2026-09-04 / ユーザー決定）が `github` と決めている。** 実測は
「local install がスナップショットである」ことを示しただけで、**source の種類に関する新事実は出ていない**。
決定を覆す根拠がないのに覆すのは禁じ手だ。加えて `directory` は**利用者が踏めない経路**であり、
A1 で確認した目的 (ii) に反する。

**[CASPAR]**: 結論: **`github` を採る（追補 1 の決定を維持）。ただし移行完了までは `directory` を併存させる。**

移行中は push 前の予行が要るため、`lam`（directory）marketplace を**暫定的に残す**。
移行完了時に削除する。これは **M-2 の quarantine 思想と同型**（消す前に復元可能な状態を保つ）であり、
新しい原則ではない。

**注意**: 併存中は `lam`（directory）と将来の github 版が**同名 plugin を提供する**。
どちらから install したかを `known_marketplaces.json` で確認できるようにしておくこと。

## Atom A4: 供給経路の可聴化

**[BALTHASAR]**: これが本議題の核心だ。「いま何が動いているか」が分からないと 2 種類の事故が起きる。

1. **stale cache**: 直したのに直らない。原因は編集が届いていないことだが、
   症状は「コードが間違っている」に見える。**今日それを実際にやりかけた**
2. **経路の取り違え**: `--plugin-dir` のつもりが install 版で動いている（またはその逆）

**[MELCHIOR]**: SessionStart hook で 1 行出せばよい。`lam-harness <version> / <経路>` を報告する。

**[BALTHASAR]**: それは**検出器を被検出物の中に置いている**。P4 後、hook は plugin 側にしかない。
**plugin が読み込まれていないケースこそ検出したいのに、検出器も一緒に読み込まれていない。**
自己参照であり、最も危険なケースで沈黙する。

**[CASPAR]**: 結論: **2 段構えにする。ただし第 2 段の実装は P4 の設計入力として渡し、本 MAGI では決めない。**

| 段 | 内容 | 守る事故 |
|:-:|:--|:--|
| **(a)** | plugin 側の SessionStart hook が `lam-harness <version> / <install or plugin-dir>` を 1 行出す | stale cache・経路の取り違え（**正常時の確認**） |
| **(b)** | **plugin の外**に「plugin が有効でなければ警告する」最小の検出を置く | plugin 自体が読み込まれていないケース |

(b) は「project hooks を全撤去する」という P4 の前提と衝突する。**衝突の解決は P4 の領分**であり、
本 MAGI は **(b) が必要だという要求を P4 へ送る**に留める（A5）。

---

## Atom A5: P4（hooks 撤去順）への影響

**[MELCHIOR]**: A4(b) のために project 側に hook を 1 本残せばよい。役割が違う（検出のみ・計器に書かない）
ので二重発火しない。

**[BALTHASAR]**: 「1 本だけ残す」は P4 の判定を複雑にする。P4 の安全性は
「**project hooks がゼロである**」という単純な事実に依存していた。1 本残すと、
その 1 本が二重発火しないことを別途証明する必要が生じる。

**[CASPAR]**: 結論: **P4 の決定は本 MAGI では変更しない。A4(b) を「P4 の設計入力」として明示的に送る。**

P4 は「セッション境界のアトミック性」という**別の未検証 crux**（配布形態 MAGI gabriel 指摘 (c)）を
既に抱えている。そこに本 MAGI から新しい要求を持ち込んで同時に解くのは、
**2 つの未検証を 1 つの相で混ぜる**ことになる。P4 着手時に (c) と併せて判断する。

## Step 5: AoT Synthesis

### 統合結論

**self-hosting の定義を「同一実体を使う」から「2 つの目的を 2 つの経路で満たす」へ更新する。**

| # | 決定 |
|:-:|:--|
| **A1** | **併用（案 D）**。既定は **install（project スコープ）** = 利用者と同じ経路 (ii)。plugin 編集直後の検証だけ **`--plugin-dir` セッション** = 編集中の実体 (i) |
| **A2** | **`version` は保持**。bump は **`/release` に紐付け**、開発ループには使わない |
| **A3** | **`github` を採る**（追補 1 維持）。移行完了まで `directory` marketplace を暫定併存（M-2 と同型） |
| **A4** | **2 段可聴化**。(a) plugin 側 SessionStart で 1 行報告。(b) plugin 外の検出は **P4 へ送る** |
| **A5** | **P4 の決定は変えない**。A4(b) を設計入力として渡す。P4 は未検証 crux (c) を既に抱えており、混ぜない |

### 先行決定への訂正

配布形態 MAGI §A3 の「維持形態は**同一リポジトリ内 plugin の local install**」は、
**上流実装（バージョン単位のキャッシュ）により (i) を満たさない**。
結論（self-hosting を維持する）は正しいが、**手段の記述が誤り**である。本 MAGI がそれを置換する。

**なぜ先行 MAGI で気づけなかったか**: BALTHASAR は条件を正しく立てていた（「local install が同一実体を
指せるかが分かれ目」）が、**それを未検証のまま結論に組み込んだ**。gabriel も 2 巡とも指摘していない。
これは 2026-09-04 の P0 実装時と同じ形である —— **実装（ここでは実行）して初めて出る誤りには
probe が構造的に届かない**。

## Atom A4'（再）: stale を何で検出するか

**[MELCHIOR]**: gabriel の言うとおり version では測れない。ならば **B（頻繁 bump）**しかない。
編集のたびに `0.1.0` → `0.1.1` → … と上げれば、update も届き、報告される文字列も変わる。

**[BALTHASAR]**: それは A2 で棄却した理由がそのまま残る —— **バージョン番号が編集回数に化ける**。

「忘れると静かに壊れる」構造を、まさに「静かに壊れる問題」の対策として導入することになる。**同語反復だ。**

**[MELCHIOR]**: では検出できない。

**[BALTHASAR]**: できる。**version を見るのをやめて、実体を比べればいい。**
キャッシュ（`~/.claude/plugins/cache/lam/lam-harness/<version>/`）とワークツリー
（`plugins/lam-harness/`）は**同じマシン上に両方ある**。差分を取れば stale は一意に判定できる。
version 文字列にも人手の儀式にも依存しない。

### Debate

gabriel は「B が唯一の候補」と述べたが、**第 3 の道がある**。gabriel はそれを検討していない。

## Atom A2'（再）: version の扱い

**[CASPAR]**: 結論: **A2 は維持する（`version` 保持 / bump は `/release`）。**

A4' で陳腐化の検出が version から切り離されたため、**gabriel が指摘した衝突は消滅した**。

## 裁定の核 —— **L1 の分解そのものが誤っていた**

L1 が「stale」「検出器」と呼んだものは、**性質の異なる 2 つの故障を 1 語で束ねていた**。

| 軸 | 問い | 故障の性質 | 検出器の置き場 |
|:--|:--|:--|:--|
| **存在（presence）** | このセッションに統治 hook が **1 つでも** 走っているか | **ガード不在 = 無音の失敗** | **plugin の外にしか置けない** |
| **鮮度（freshness）** | 走っている hook は **いま編集している実体**か | **QA の空振り = 誤った確信** | **plugin の中にしか置ける**（出所は読み込まれた実体自身が `__file__` で知る） |

**争点 2（自己参照の罠）は存在軸にだけ当てはまる。** 鮮度軸で plugin 内に置くのは自己参照ではない ——
plugin が読み込まれていないなら鮮度は問題にならず、存在軸の検出器が拾う。
**L1 も gabriel も「検出器」を 1 個の部品として置き場を争ったため、A4 と A5 が同時に未決になった。**

## さらに「stale」の定義が誤っていた

**「キャッシュ ≠ ワークツリー」は開発中は常に真である**（実測: 今日 install したキャッシュは既に差分を持つ）。
これを警報にすると `security-commands.md` が自ら警告する「**常時鳴る計器は殺される**」型に直行する。

真の hazard は「**キャッシュから走っているセッションで `plugins/lam-harness/**` を編集した**」という
**セッション局所の事象**である（その編集は今のセッションに効かない）。
**差分の有無は状態報告（`git status` と同じ扱い）、編集-on-cache が警報。**
