## 記録 5: W0-M1-T8（HGA #17）crux 3 本への回答と M-1 進行への影響

**判定: `revise`**（小規模改訂 / 新 Task を増やさない形 / W1 は改訂後ただちに進めてよい）。

### crux 1: この設計のままで M-1 は「出口」になるか

**回答: ならない。現設計のままでは「次の階層」である。**

欠陥は決定木の中ではなく**外側の 2 欠落**にあると指摘された:

- **流入制御の不在** — ストック（≈750 行）への一回性処理であり、フローに触れていない。数 Milestone 後に同じ棚卸しが必要になる = 定義上 M-2
- **大域的終了条件の不在** — 5 値閉集合の閉性は verdict の閉性であって、Milestone ジャンルの閉性ではない

さらに第 3 の欠落として **基質適合テストの不在**。軸 4（根拠 = 発火実績）の観測はすべて Opus 4.x 以前の基質で採られており、**旧基質での発火は新基質での必要性の証拠にならない**。

内部証拠として、W0 で計器較正に 2 Task を消費した事実自体、および `rule-002` が `rule-001` 型 drift の保守のために存在することが挙げられた —— **機構は監査面を増やし、監査面は issue を増やす**。

### crux 2: 「運用移管」を判定値に加えるべきか

**回答: 加えるべき。ただし 3 必須フィールド（観測シグナル / 監視面 / 失効日）と同時保有上限つきで。**

核心は「**リスクを機構なしで受容する決定は、それ自体が軸 1 のユーザー意思（リスク許容度の宣言）**であり、現行の『削減』で処理すると統治判断が台帳に無記録のまま消える」。

無条件追加が棄却された理由も明快で、監視面のない運用移管は「削除の婉曲語」か「誰も実行しない ops 負債」に退化し、**ops チェックリストという名の新 rules ファイルとしてループが再発する**。最希少資源は単独ユーザーの注意である。

### crux 3: 運用移管の適用条件は何か

**回答: 3 条件の同時充足。**

1. **発火が無計装でも喧しい**（主ゲート）— 機構の存在理由は沈黙する失敗の検出であり、失敗が自ら騒ぐなら機構は冗長。逆に静かに潜伏する類（データ破損・セキュリティ）は**永久に運用移管不可**
2. Phase A（veto 先行スクリーニング）通過済 = 可逆・爆風半径有界
3. 発火頻度 × 復旧コスト < 機構維持コスト（**機構が将来の監査対象面になる二次コストを算入**）

あわせて意味論の三分が示された: **deferred = 未決定**（tracker に居座り以後の全 design doc に再出現。R1-054〜058 が実証 = **在庫自体がループ燃料**）/ **characterization pin = 観測の機構化・判断の先送り** / **運用移管 = 決定済み・非機構化を選択・クローズ**。

### M-1 の進行に与えた影響（方式変更あり / Task 増ゼロ）

改訂 5 点はすべて**既存 Task の定義に畳み込まれ、Task はゼロ増**で処理された。方針は Fable 原文の引用が正確に示している —— 「**34 Task の手続きが病であるとき、処方箋に Task を足すのは病の進行である**」。

| # | 改訂 | 反映先 | 実績 |
|:-:|:-----|:-------|:-----|
| 1 | 運用移管を第 6 値として追加 | W0-T4 / W1-T5 / W1-T6 / W2-T5 | **2 件が実際に運用移管された**（記録 3） |
| 2 | Phase B の立証責任を反転（保全にのみ理由必須） | W1-T5 | **削減 27 件（判定行の 54%）** = 反転が効いた |
| 3 | 基質適合テスト「Opus 5 は指示なしでこれをやるか」 | W1-T5 | 21 条項中 **16 件が無効化**、ただし **TDD 系 4 件は全件通過**（後述 Keep 2） |
| 4 | 出口宣言 3 点を DoD-7 として新設 | requirements DoD-7 / W4-T5 | **本 retro で宣言**（後述） |
| 5 | gabriel は基質適合テストを通過しうる | W1-T5 | W1 で個別判定済 |

## 出口宣言 3 点（DoD-7）

M-1 が「監査 → issue 起票 → consolidation → さらに監査」というメタ階層の**次の階層**ではなく**出口**であることを成立させるため、以下を宣言する。

### (a) 一回性宣言

**M-1 は一回性の Milestone であり、consolidation 系 Milestone のジャンルをここで閉じる。**

「規範文書が肥大化していないか」を問う棚卸しを、今後 Milestone として再度立ち上げない。

### (b) 決定木の転用（流入制御）

**以後この決定木（4 軸 + 基質適合テスト + 6 値）は「新規条項の誕生ゲート」として適用し、定期棚卸しとしては再実行しない。**

すなわち、新しい規範文を追加しようとする時点で決定木を通す。ストックを定期的に洗うのではなく、フローの入口で止める。

### (c) no-net-growth

**規範負荷の総量に「新条項 1 追加 = 既存から同等量の削減」を課す。**

計測対象は「**規範ストック総量**」（無条件ロード・条件ロードの別を問わない全条文量）とする。予算計測を起動時ロード量に置くと、「`paths:` を付けて予算準拠を装いながらストックは成長し続ける」というゲームが可能になり、ループ抑止という予算の目的が空洞化するため。無条件ロード量は**別途の性能指標**として観測してよいが、予算そのものではない。

### 対象外（明示）

**upstream 仕様突合は本宣言の対象外。** 本宣言が閉じるのは「条項の内容が過剰か」を問う consolidation 系のジャンルである。「LAM の機構が Claude Code の公式仕様と重複・矛盾・陳腐化していないか」を問う upstream 仕様突合は**別ジャンル**であり、M-1 の 4 軸では原理的に捕捉できない。

M-1 期間中の実例: `paths:` 機能を使っていなかったこと / `/doctor` の trim 機能を認知していなかったこと / ADR-0001 が `command` を agents の `model:` 値と取り違えていたこと —— **いずれも軸 2 でも軸 4 でも検出できない**。M-1 完了後に別途実施する（入力リストは `docs/artifacts/upstream-inventory-input.md`）。

## Keep / Problem / Try

### Keep 1: 委譲の可否を「検証コマンドが 1 行で書けるか」で決めた

W4 の 5 Task はこの基準で振り分けた。結果、**外部の不動点がある作業（pytest / 件数突合 / 測定コマンド）の委譲は全件成功し、判断そのもの（固有度の確定 / 配布可否 / retro）は L1 が持った**。

特に効いたのは**親検収**である。L3 の測定報告に Wave 取り違えが 1 件あり、L1 の再実行で捕捉した。数値自体は全件一致していたため、報告の本文だけを読んでいたら通っていた。

### Keep 2: 基質適合テストは「内側の検査」だけを落とした

改訂 3 の実測結果は明快だった。21 条項のうち 16 件が「Opus 5 の既定挙動」として無効化されたが、**TDD 系 4 件は全件が保全側に残った**。

分岐している基準は「その条項が問うているのは**内側の検査**か、**外部との突合**か」である。自己検証は自分の理解の内側でしか働かず、仕様やテストとの突合は機構でしか担保できない。**自律性が上がるほど TDD の重要性は増す**という結論は、削減 Milestone の中から出てきた点で価値がある。

### Problem 1: 判定軸が「守備範囲」しか見ておらず、現役部品を死んだ部品と誤認しかけた

W3-M1-T3 で `code-reviewer` の統廃合を提案した。design §7.3 の 2 指標（agent-memory が 1.5 か月未更新 / `description` が `quality-auditor` の真部分集合）に従えば削除に進む流れだった。

実際には `/full-review` Stage 2 が**観点別に 3 並列で起動する現役部品**であり、`lam-orchestrate` の分配表・テスト 2 本・`fable-l3-protocol.md`（PM 級）からも参照されていた。指標 1 が稼働実態を捉え損ねた理由は単純で、**`full-review` 経由の起動では agent が memory を書かない**。「memory の更新日 = 起動実績」という前提が成り立っていなかった。

さらに決定的だったのは、**真部分集合であることこそが `code-reviewer` を「安い並列ワーカー」にしている**点（97 行 vs 328 行）。包含関係は統合の根拠ではなく**役割分化の結果**だった。「守備範囲が包含される」と「統合すべき」は別の命題である。

→ 撤回して `description` の書き分けに着地。**統廃合判定には「呼び出し側の実参照」を軸として加える。**

### Problem 2: 配布 2 経路が成果物の一部を覆っていない

FR-18 の 2 経路（規律 = カタログ / skills・agents = plugin）に対し、`verify_model_reference.py` とそのテストは**どちらにも属さない**。結果として、カタログ経由で `model-roster.md` のパターンを持ち帰っても、**その SSOT を守る drift 検査機構は付いてこない**。規律だけが移り、規律を守らせる機構が残る。

これは実行漏れではなく設計上の隙間である。配布コピー（`D:\work7\規律の条項トリアージ-他プロジェクト提案-2026-07-26.md`）§6 に正直に記載した。

### Problem 3: 「未確認」と明記された前提だけが着手時に検査された

design §8.3 は配布コピーの書き出し先を「未確認 / W4 着手時に確認」と明記しており、実際に W4 着手時に確認して前例を特定できた。**明記された不確実性は機能した。**

一方、「plugin 版と LAM 版の skill が同一であるか」は**問いとして立てられていなかった**ため、W4 着手まで検査されなかった。実測では plugin 版は汎化された fork であり、「version bump = コピー」という design の前提が成立していなかった。

**明記されなかった前提は最後まで検査されない。** upstream-first 原則は「未確認と明記せよ」を強制するが、**問いのリストを生成する機構ではない**。

### Try 1: 委譲先に渡す停止条件を、判断ではなく観測可能な出力で書く

FR-16 の動作確認 probe で、停止条件を「最初の実作業ステップを開始できるまで」と散文で書いた結果、`references/` への遷移が 1 度も起きず 1 ラウンドを空振りさせた。第 2 ラウンドで「**読んだファイルのフルパスを列挙せよ**」という観測可能な出力に変えたところ機能した。

**当初これを「F1 の適用漏れ」と記述したが、条文を読み直して訂正する。**

F1 の適用対象は「**依頼文中**の名詞（ファイル名・関数名・「〜のはず」）に仮定タグを付ける」であり、**依頼文＝L1 に来る依頼**を指す。**L1 が subagent に出す委譲プロンプトは F1 の対象外**である。したがってこれは条項があるのに運用しなかった「適用漏れ」ではなく、**条項が当該場面を覆っていない「適用範囲外」**である。

この区別は処理を変える。適用漏れなら運用改善で閉じるが、範囲外なら実際の隙間であり、埋めるには条項が要る。

**ただし今 Milestone では条項を追加しない。** 軸 4（根拠）は条項の誕生に **2 検出イベント**を要求しており、本件は 1 件目だからである。

→ **本件を「委譲プロンプト設計における仮定タグ不在」の検出イベント 1 件目として記録する。** 2 件目が発生した時点で `trust-model.md` §閾値（2 回）の既存フローに合流し、出口宣言 (b) の誕生ゲート（4 軸 + 基質適合テスト）と (c) の no-net-growth を通したうえで採否を判断する。**新条項ゼロ / 新機構ゼロ**（既存ループの入口に接続するだけ）。

> **基質適合テストの予備判定**: 「Opus 5 は指示なしで、自分が書く委譲プロンプトの前提に仮定タグを付けるか」— 本セッションの実測は **No**（1 件）。ただし 1 データ点であり、2 件目まで判定を確定させない。

### Try 2: 委譲先の報告が長くなる場合は、成果物をファイルにする

retro 素材の抽出で、L3 に「5 素材を報告せよ / ファイルは作らない」と指示した結果、**最終メッセージに最後の 1 素材しか残らず 4 素材が失われた**。往復せず L1 が直接取り直した。

「ファイルを作らない」制約は、報告が短い probe には有効だったが、長い抽出には不適だった。**報告の長さに応じて成果物の形式を選ぶ**（短い判定 = メッセージ / 長い抽出 = ファイル）。これも Try 1 と同じ「出力契約を観測可能にする」の系である。

### Problem 4: M-1 は規範の重複を減らしながら、記録の重複を増やした

M-1 は相互参照する成果物を **11 個**生んだ（`m-1-baseline-w0`〜`w4` / `clause-ledger` / `triage-table` / `stability-gate` / `distribution-catalog` / `retro-M1-W1` / 本ファイル）。

pytest 件数・規律本体の文字数・PM 級ダイアログ発火数・条項件数といった数値は、それぞれ **4〜6 ファイルに重複して載っている**（baseline 系は各 Wave が前 Wave の値を再掲する構造であり、台帳・トリアージ表・カタログ・retro は件数を共有する）。**そしてその整合を検査しているのは L1 の注意だけである。**

W4 で発生した数値の誤り 2 件は、いずれも推論の誤りではなく**ファイル間整合の誤り**だった:

| # | 誤り | 型 |
|:-:|:-----|:---|
| 1 | L3 の測定報告で W2 末の値を W3 末と取り違え | 5 つの baseline ファイルにまたがる同種の数値の混同 |
| 2 | L1 自身が W4 の PM 級発火数を 0 と記録（実際は 1） | 測定時点と変更時点の乖離を再導出しなかった |

**規範ストック（166,638 字）は測ったが、記録ストック（11 ファイル × 重複する数値）は測っていない。** M-1 の測定 6 項目に、成果物の相互整合を見る項目はない。

LAM はこの種の問題の道具を既に持っている。`verify_model_reference.py` は「同じ事実が複数ファイルに散っている状態を機械で突合する」スクリプトそのものである。**M-1 はその道具を自分の成果物に向けなかった。**

> **本 Problem に対して M-1 では対処しない。** 対処は新規の検査機構の追加であり、HGA #17 の指摘「**機構は監査面を増やし、監査面は issue を増やす**」に正面から当たる。次に同種の Milestone を立てる判断をする人間が、この記録を入力として使えれば足りる。

### Try 3: `permission-levels.md` の表記を実装に合わせる（記録のみ / 実施しない）

`permission-levels.md` のパスパターン表記は `docs/specs/*.md` だが、実装（`_hook_utils.py`）は `^docs/specs/.*\.md$` で深さ無制限に一致する。実配置は `docs/specs/<milestone>/*.md` の深さ 2 であり、**表記だけを読むと捕捉外に見える**。

統治の穴ではない（実装は正しく捕捉している）。表記の精度の問題であり、**修正すれば 1 文字の話だが PM 級ファイルの編集を要する**。出口宣言 (c) の no-net-growth に照らし、単独では実施せず、次に `permission-levels.md` を触る機会に同梱する。
