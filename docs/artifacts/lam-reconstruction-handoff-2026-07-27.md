## §2 発端（ユーザー発言の逐語 / 要約しないこと）

### 第 1 発言

> 常駐指令 50 目標のことになるんだけれども、そのためには、通常の再査定だけでは足りないはずである。では何をしたらいいのだろうか。**解体的な再構成**を考える必要があると思う。場合によっては **LAM という名前を変えてもよいという決意**が必要さえあるかもしれない。そのためにまず、**LAM の本質は何か**ということを考え、導き出さねばならない。その際には**ユーザーの意思を守るという大前提も外して考える必要がある**だろう。今の状況、つまり常駐指令を減らすことが出来ないのは、あなたがこれまでの指令削減で述べている「**ユーザーの意志というのは外せない**」という大前提があるからだ。

指示: HGA・MAGI を使う / HGA に**ネット検索・ローカル検索の権限**を与え「**関係無いかも知れないと思うような広めの情報**」を渡す / **通常の採算・ルールは一旦無視**し、必要と思われる措置は何でも行う。

### 第 2 発言（位置づけの裁定）

> LAM はもともと私自身が使用するための道具であった。しかし、その出来が良いために、GitHub でパブリックリポジトリとして公開することにした。そこには**有名になりたい、認められたいというような心理があったのは間違いない。そして、この動機は未だなくなってはいない**。それを考えると、LAM は配布できるようにしておくべきだろう。

### 第 3 発言（自己撤回 / **本セッションの転換点**）

> ただし更にその内側「**私的なツールの出来が良かったら配布することにした**」があることが、若干の引っかかりをもたらします。**配布するために出来が悪いものを使う、というのは本質では無い。** そしてセルフホスティングを捨てると、**作られた製品を試すということができなくなる**。これは多人数のチームであればそんなことはないわけであるが、**個人でやっている場合にはその負荷には耐えられない**。それを考察すると**セルフホスティングを捨てるという思考実験は間違い**ということになる。その上で移住をするにしてもしないにしても、**八十条項の全数判断をする**。これは**私の知的な統治記録を持ち出さない、もしくは外す、配布物から外すという決断に結びつけて考える**ことになるだろう。

### 第 3 発言から導かれた設計原則（L1 が抽出 / memory に記録済）

| | 順序 |
|:---|:---|
| 通常の製品 | 顧客のために作る → 自分でも使う（dogfooding は手段） |
| **LAM** | **自分のために最良のものを作る → 出来が良ければ配る（配布は結果）** |

⇒ **配布は上流に立てない。配布可能性を理由に自分の道具を劣化させる決定はすべて誤り。**（ユーザー自身が floated した「開発側は素の Claude Code でよい」案も、この原則で却下される）

## §4 外部調査の要点（一次 fetch 済 / **再調査不要**）

| 事実 | 内容 |
|:---|:---|
| **天井 80 の出典 = arXiv:2607.19257**（Netanel Eliav 単著 / 2026-07-21 / *Prompt Design at Scale* / **実在確認済**） | perfect-response rate は **N=10 で 0.588-0.938 / N=40 で 0.094-0.312 / N=80 で 0.000-0.019**（全モデル・全フォーマットで実質ゼロ）/ N=120+ も 0。§8 の推奨は逐語 **"Treat roughly 40 simultaneous instructions as a redesign point, not a tuning point"** および **"splitting it across turns, tools, or a validation pass is a more reliable response"**。評価モデル = Claude Sonnet 5 / Claude Haiku / Gemini Flash / Qwen 27B / Qwen 35B（**Opus は含まれない**）。per-instruction adherence はフォーマット差 ±2-5pt で "measurable" なまま |
| **ただし LAM への転移は不成立** | 論文の N は「**1 出力に同時拘束される指令数**」。LAM の常駐 80 は 1 ターンに同時発火しない（PLANNING 条項は BUILDING 中は休眠）。**per-turn 実効同時指令数は未計測**（HGA #21-A の推定は 1 桁〜10 台）。真の被害軸は adherence ではなく **attention budget / context rot = トークン量** |
| IFScale（arXiv:2507.11538 / Jaroslawicz et al.） | 500 指令で最良モデル 68% accuracy。**reasoning モデルは 100-250 指令の中密度までほぼ完璧**を維持してから劣化。**primacy bias**（先頭の指令が優遇される）あり |
| **Claude's Constitution**（2026-01-21 / 84 頁 / 逐語 fetch 済） | **規則を残すべき 3 条件**: "when the costs of errors are severe enough that **predictability and evaluability** become critical" / "when there's reason to think **individual judgment may be insufficiently robust**" / "when the absence of firm commitments would create **exploitable incentives for manipulation**"。既定は "We generally favour **cultivating good values and judgment over strict rules**" |
| Claude Code 公式（memory / skills） | CLAUDE.md は "target under **200 lines** ... Longer files consume more context and **reduce adherence**"。変換規則: "**If the instruction is something that must run at a specific point ... write it as a hook instead**"（"apply **regardless of what Claude decides**"）/ "a section of CLAUDE.md has **grown into a procedure rather than a fact**" → skill 化。**MEMORY.md には 200 行 / 25KB の機構的上限が実装済**（**CLAUDE.md には非適用と明記**）。`/doctor` の trim 判定基準 = "cuts content Claude can **derive from the codebase** ... keeps **pitfalls, rationale, and conventions that differ from tool defaults**" |
| Anthropic context engineering | "**context rot**"（トークン増で性能劣化）/ モデルは有限の "**attention budget**" を持つ / 原則 "the **smallest possible set of high-signal tokens**" / "a **laundry list of edge cases**" を詰め込むな、代わりに "**curate a set of diverse, canonical examples**" |
| **総量が実際に減った 3 実例** | ① **British Columbia**（2001-2019）: 規制**要件** 37% → 累計約 50% 削減。鍵は**計測単位の変更**——「2,200 本の規制」では動かず、「**382,139 個の regulatory requirements**」に割り直した瞬間に削減が実務作業になった。+ 専任**大臣** + two-for-one → 恒久 one-in-one-out ② **UK Statute Law (Repeals)**: 専任の独立機関（Law Commission）が**単一かつ低い基準**（"**no longer of practical utility**"）で**一括法案**として処理。1965 年以降 3,000+ Acts 廃止（2013 年単独で 817）③ **policy termination** = **de-alignment**（作った側と所管側の展望の乖離） |
| **3 例の共通構造（外部調査の中心的発見）** | **削除を、作成と同じ主体・同じ手続・同じ粒度に置いていない**（(a) 別主体 / (b) より低い判定基準 / (c) より細かい単位 / (d) 一括処理）。逆に、削除を作成と同じゲートに載せている限り削除は常に作成より高コストになり、**ラチェットは外れない** |

| 憲法の改正硬性 | **硬性は追加も削除も等しく難しくする**。追加だけ硬く・削除を柔らかくしない限り、硬性はラチェットを**強める** |

## §10 L1 の考察（現在の見立て / **§11 の警告と併せて読むこと**）

**今日、削減案が 5 回壊れた。そして壊れ方が一貫している —— 削ろうとしたものが、必ず別の機構の入力になっていた。**

| 削ろうとしたもの | 何の入力だったか |
|:---|:---|
| 非指令 14 件 | **計器の定義**（触れば再採点） |
| フェーズ繋留条項 | **`current-phase.md` の信頼性** |
| self-hosting | **製品の唯一の QA** |
| 埋込散文 18% | **§9 = 次世代の失効判定材料** |
| R4 退避 | **余裕ゼロの交換レート** |

これは**密結合の症状**であり、密結合は SSOT 化と機構化を推し進めた結果である（M-1 retro が既に「機構は監査面を増やし、監査面は issue を増やす」と実測 / HGA #18 の自己修正 2 は「病理は『機構であること』ではなく『**散文に結合した機構であること**』」）。

> **LAM が減らせないのは、LAM がよく設計されているからである。冗長性がないから、削る余地がない。**

したがって処方が変わる。**減量が可能なのは冗長な系だけ**であり、密結合な系で総量を減らす唯一の方法は**機能を捨てること**。すなわち「80 → 50」は「**LAM の機能を 3/8 捨てる**」と同義である。

そして決定的な事実: **本セッション（2026-07-27）だけで、HGA 召喚・MAGI 合議・gabriel 検証・誕生ゲート台帳・triage 表・権限等級・upstream 裏取り・TDD 内省の復活経路——そのほぼ全部が実際に使われた。** 経路 2 の単一基準「最後に実際に効いた場面を 1 つ指させるか」を適用すると、**今日がその場面になってしまい、大半が残る**。

**問いは「どの指令を消すか」ではなく「LAM のどの機能を諦めるか」ではないか。** これは技術的判断ではなく、ユーザーが何を手放せるかの問いである。

## §12 HGA #23 に当てる crux（召喚するならこれ）

### 主 crux

> **5 回連続で削減案が壊れ、壊れ方が「削ろうとしたものが別の機構の入力だった」で一貫している。これは (a) まだ正解が見つかっていないからか、それとも (b) 系が正しく『減らすな』と言っているのか。**
>
> (b) であるなら、「常駐指令を減らす」という目標設定自体が誤りであり、**置き換えるべき問いは何か**。

### 副問（優先順）

1. **§10 の密結合診断は正しいか、それとも L1 の合理化か。** L1 は「自分を縛る規則を削りたい」と「自分が使う道具を守りたい」の**両方向の利益相反**を持つ。5 回否定された後に系を擁護し始めた事実をどう読むか。
2. **「機能を捨てる」に踏み込むなら、捨てる候補の順序は何か。** 判定基準は Claude's Constitution の 3 条件（誤りコスト / 判断の頑健性 / 操作の誘因）で足りるか。
3. **経路 2 の単一基準は、今日のセッション自身によって無効化されていないか。** 「最後に効いた場面」を問う基準は、直前に全機構を使ったセッションの後では機能しない。基準の再設計が要るか。**代替として「効いた場面」ではなく「効かなかった場面」を問う反転形は成立するか**。
4. **経路 1 のスコープ修正**: 「次世代の判定材料」を除外した後、実際に何文字が残るか。そもそも「統治記録を規範ファイルから剥がす」は正しい方向か（**剥がした先で誰が読むのか** / 剥がすと §9 型の「判定材料の消失」が別の場所で再発しないか）。
5. **守勢（経路 5）を採る場合、「新規流入ゼロ維持」は現行の誕生ゲートで足りるか。** 足りないなら何を足すか（**ただし足せば天井を超えて net-negative が発動する** = 自己言及的な罠）。
