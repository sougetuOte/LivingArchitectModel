## §1 これは何をする Milestone か

**LAM を配布したときに、開発者個人の私物まで一緒に渡してしまっている。どれが製品でどれが私物かを決める。**

現在の配布物は**リポジトリの全内容**である（README の 3 経路はいずれもリポジトリを丸ごと渡す）。そこには開発者個人の PC のパス（`D:/work7/Fable-Alembic`）、個人の予算枠・モデル選択方針、外部リポジトリとの連携規律が含まれており、**31 回のリリースすべてで配られてきた**。

判定基準は既存の枠組みを流用する（**新しい判定軸を作らない**）:

> **「この条項は私の環境・予算・他プロジェクト・個人名を参照するか」**
> （handoff §6「経路 2 の 2 列」の**配布列** / ほぼ機械判定）

背景・発端・なぜこれを Milestone として立てられるのか → **[d-1-rationale-2026-07-27.md](../../artifacts/d-1-rationale-2026-07-27.md)**

## §3 要件

### 機能要件

| ID | 要件 |
|:--|:--|
| **FR-1** | 判定基準は §1 の**配布列を流用** **MUST**。新規の判定軸を追加すること **MUST NOT** |
| **FR-2** | 実装は**既存の配置・機構の再利用を優先** **MUST**。マニフェストを支える**検査群・分類学・メタデータ列を新設**すること **MUST NOT**（マニフェスト自体は FR-3 の成果物であり禁止対象ではない）。実装手段は design で決定（§5 未決 6） |
| **FR-3** | 判定結果は**パッケージング境界**として表現 **MUST**（形式は §5 未決 1）。リポジトリを分割すること **MUST NOT** |
| **FR-4** | 判定対象は **R1 の 15 ファイル**とする **MUST**（§2 のとおり skills / agents / hooks は対象外） |
| **FR-5** | 判定結果は**単発の記録**として残す **MUST**。定期再判定の手続を条文化すること **MUST NOT** |
| **FR-6** | 配布物から除外した資産について、**除外後も self-hosting が成立する**ことを確認 **MUST**（開発環境では引き続き全資産が有効であること） |

### 非機能要件

| ID | 要件 |
|:--|:--|
| **NFR-1** | §A 常駐指令カウントを増やさない **SHOULD**（増やす場合は誕生ゲートを通す **MUST**） |
| **NFR-2** | **判定者はユーザー本人** **MUST**。L1 / L2 / L3 の**事前採点**を用いること **MUST NOT**<br>**線引き**: 許すのは**結論を出さない情報提示**（パス・個人名・予算数値・外部リポジトリ参照の検出と提示）。禁じるのは**採否・分類の判断**（下書き・優先度づけ・推奨の付与） |
| **NFR-3** | 「何が配布物か」の**検査機構**を新設すること **SHOULD NOT** |

## §4 成功基準

1. **R1 の 15 ファイル全件について配布 / 非配布が決まっている**（未判定ゼロ）
2. **判定結果に従って実際に配布物を作れる**（手順書だけでなく実行可能であること）
3. **`_OUTBOUND_WRITE_BAN_ROOTS` の無条件実在検査を置けるようになる**、**または**「置かない」判断の根拠が記録されている（発端の詰まりが解けたことの観測可能な指標）
4. **self-hosting が壊れていない**（開発環境で pytest 全系統が緑 / 現在 1182 passed + 14 skipped）
5. **§A 指令カウントが 80 を超えていない**
6. **retro で WC-11 防御の成否を確認している** —— 「次も同じやり方でやろう」と言える状態になっていないこと

## §5 未決事項（design で答える）

| # | 問い | 注記 |
|:-:|:--|:--|
| 1 | **パッケージング境界の表現形式** | ファイル 1 枚 / frontmatter 拡張 / `.gitattributes` 等 |
| 2 | **`fable-l3-protocol.md` の扱い** | 全体を非配布とするか、L3 導入部のみ分けるか。**「分ける」を選ぶ場合、それが手 4（埋込統治記録の剥離）の先取りでないことを明示的に判定 MUST**（FR-3 が禁じるのはリポジトリ分割であってファイル内容分割ではないため、§2 のスコープ除外を自動的には守れない） |
| 3 | **除外資産の置き場** | リポジトリ内に残して選別するか、非ロード領域へ移すか |
| 4 | **判定作業の実施単位** | 15 件を一度にか、分割するか |
| 5 | **成功基準 3 の解決先** | 無条件検査を置くか、置かない判断にするか |
| 6 | **実装手段** | **α** `init-harness` を選別機構に拡張（新規機能の追加になる）/ **β** 配布時の除外（`.gitattributes export-ignore` 等 / template・clone 経路への効き方が要検証）/ **γ** リポジトリ内の配置で解く（「統治記録は R1 の外」の前例あり）/ **δ** 配布を諦めて明示（決定 2 と衝突） |
| 7 | **将来 R1 に追加されるファイルの判定責任** | 成功基準 1 は現在のスナップショットを条件にしており、誕生ゲート経由で R1 が増えた瞬間に未判定が生じる。しかし FR-5 が定期再判定の条文化を禁じる。**新規機構を作らずに**漏れを防ぐ経路を決める **MUST**（候補: 誕生ゲートの既存ステップに配布列の 1 問を足す） |
