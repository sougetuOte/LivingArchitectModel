## §0 なぜこの Milestone を立ててよいのか（合法性の根拠）

> **v1.2 で根拠を差し替えた（2026-07-27 / spec-critic の critical 指摘を反映）**。初版は `CHANGELOG.md` の「次 Milestone の性格の明示」を主根拠に置いていたが、**その一節は撤回された移住ブロックに属し、「存続する決定」の列挙（決定 2 / 決定 4 / 取引 #1 の erratum / 主権的解除の非先例化記録）に含まれていない**。L1 の「移住は撤回されたがジャンル判定は撤回されていない」という読みは解釈であって、CHANGELOG 側にも MAGI / gabriel / HGA のいずれの裁定にも明示の裏づけがなかった。**この読みを根拠として復活させないこと。**

### 主根拠: ユーザーによる明示的な判断（単発 / 日付つき / 非先例化）

M-1 の出口宣言 (a)「**consolidation 系 Milestone のジャンルをここで閉じる**」は、**ユーザー自身が立てた制約**である。したがって「本件が (a) の対象か否か」の判定権はユーザーにある（`CLAUDE.md` Hierarchy of Truth § User Intent が最上位）。

**2026-07-27 セッション 17 において、ユーザーは以下を経て本 Milestone の起票を指示し、ジャンル判定への明示的同意を与えた**:

1. L1 が承認要求で「§0 のジャンル判定に明示的に同意いただきたい。ここが崩れると Milestone 自体が成立しない」と提示
2. ユーザーが「承認」と応答

これは **WC-9a「メタ意思の常設化」への防御形式（日付つき・単発・非条項化）に従う**（handoff §7 が「WC-9a/9b は主権的解除の記録形式で当面の防御が立っている」と記録）。**「ユーザーが認めれば Milestone を立てられる」を反復可能な規則として残さない。**

### 補強: 経路 2（主権審査）の配布列と主題が一致する

handoff §6「生きている案 #2 = 主権審査」は **2 列**で構成され、そのうち**配布列**は本 Milestone の主題そのものである。

| 列 | 問い | 解く問題 |
|:--|:--|:--|
| 残留列（G1） | 「この条項が最後に実際に効いた場面を 1 つ指させるか」 | 常駐面の重さ |
| **配布列（G2）** | **「この条項は私の環境・予算・他プロジェクト・個人名を参照するか」** | **配布物の選別** ← **本 Milestone** |

handoff は同案について「**ユーザーが実施を宣言済み**」と記録し、出力先を「**パッケージング境界（マニフェスト）へ流し、リポジトリは割らない**」と定めている。本 Milestone の FR-3 はこれと一致する。

**なお本 Milestone は配布列のみを扱い、残留列（G1）には触れない**（残留列は常駐面の質量を問う = consolidation 寄り / 下記スコープ除外を参照）。

### WC-11「主権審査の制度化」への回答（正面から答える）

> WC-11: 「ユーザーがやれば合法」が反復可能な手続として認知され、(a) が閉じた consolidation ジャンルが**主権の扉から帰還する**（今度はユーザーの注意を燃料にして）

**主権審査を Milestone 化する行為そのものが WC-11 の機序に触れる。** これを認めた上で、以下 3 点で防御する。

1. **D-1 は単発とする。** 「配布境界 Milestone」を反復可能な型（テンプレート・手順・スキル）として残さない（**FR-5**）
2. **審査の結果は記録し、審査の手続は条文化しない**（handoff §7 WC-11 の防御そのまま）
3. **扱うのは配布列のみ**。残留列（consolidation 側）を D-1 に持ち込まない

**D-1 完了後に「次も同じやり方でやろう」と言えてしまう状態になっていたら、防御は失敗している。** retro でこれを確認すること。

### ジャンルの区別（判定の内容）

| | (a) が閉じたもの | 本 Milestone |
|:--|:--|:--|
| ジャンル | **consolidation 系** —— 規範文書が肥大化していないかを問う棚卸し | **製品定義の変更** —— 何を配布物とするかを決める |
| 問い | 「この条項は要るか」 | 「この条項は**誰のものか**」 |
| 出力 | 条項の削除・移動 | **パッケージング境界** |

### スコープに入れないもの（重要）

**手 4（経路 1 = R1 内の埋込統治記録の剥離）を D-1 に含めない。** 手 4 は常駐面の質量を問う作業であり consolidation 寄りである。製品定義 Milestone に同梱すると **(a) の脱法**になる。手 4 は引き続き Milestone 外の「手」として扱う。

### 1.1 発端となった具体的な詰まり

`.claude/hooks/pre-tool-use.py` の不可逆ガードに、開発者個人の環境の絶対パスが埋まっている。

```python
_OUTBOUND_WRITE_BAN_ROOTS = (Path("D:/work7/Fable-Alembic"),)
_OUTBOUND_WRITE_ALLOW_ROOTS = (Path("D:/work7/etc-to-alembic/handoff"),)
```

MAGI はこれを「パスの修正」として直すことを**否決**した（兄弟導出 / 設定ファイル化 / 条文パースはいずれも死因つきで記録済）。沈黙の検出は所有者ゲートつきテストで解決済み（commit `6689bd0`）。**残ったのは、この定数が参照する `.claude/rules/fable-l3-protocol.md` が R1 = 配布物に含まれている**という事実である。

### 1.3 現在の配布チャネル（2026-07-27 実測 / **初版の誤りを訂正**）

> **訂正の記録（v1.1 / 2026-07-27）**: 初版の FR-2 は「`init-harness` の**既存選別機構**を実装先とする」と定めていたが、**そのような機構は存在しない**。L1 が背景タスクに書いた未検証の記述を requirements に持ち込んだもので、**承認後に実物を読んで判明**した。`upstream-first.md` §設計フェーズへの適用（「設計書に具体を書く前に裏取りする」）の不履行である。**この誤りを再導入しないこと。**

`init-harness` の実体（`SKILL.md` + `references/templates.md` 実測）:

- 空のディレクトリ 6 件と**雛形ファイル 6 件**（`CLAUDE.md` / `CHEATSHEET.md` / `CHANGELOG.md` / `SESSION_STATE.md` / `.claude/current-phase.json` / `.claude/harness.json`）を**インライン文字列から生成**する足場組みスキル
- **`.claude/rules/` への言及はスキル本体にもテンプレートにも存在しない**（grep 実測 0 件）
- したがって LAM の資産を選別して配る機能を持たない

**実際の配布チャネルは README「使い方」の 3 経路であり、いずれもリポジトリを丸ごと渡す**:

| Option | 方法 |
|:--|:--|
| **A（README 推奨）** | GitHub の "Use this template" |
| **B** | `git clone` → `rm -rf .git && git init` |
| **C** | ZIP 展開 → Claude に「配置してください」と指示 |

**Option B の直後**に「LAM は `.claude/`、`docs/internal/`、`CLAUDE.md` が連携して動作するため、**一式をそのまま使うことを推奨します**」とあり、**Option C** も「LAM の全ファイルを確認し必要な部分を適応させてください」と全量提示を前提にしている（引用元を Option 別に特定 / v1.2）。

**帰結**: **現在の配布物 = リポジトリの全内容**である。`fable-l3-protocol.md` / `hga-summoning.md` / `D:/work7/Fable-Alembic` のハードコードは、**31 回のリリースすべてで配布されてきた**。

### 1.4 self-hosting との関係（制約）

HGA #22 が「**self-hosting は原則ではなく LAM 唯一の QA 機構**」と裁定した。したがって:

- **開発環境と配布物をリポジトリ境界で分けてはならない**（移住 = 死んだ案 #5 / ユーザー撤回済）
- 境界は**パッケージング境界**（マニフェスト）として実装する
- 2026-07-27 の WSL2 検討で ① 現状維持が確定した理由も同根（**WC-12「dogfooding の名目化」のプラットフォーム版**）

## §3 要件（RFC 2119）

### 機能要件

| ID | 要件 |
|:--|:--|
| **FR-1** | 配布物と非配布物を判定する基準を明文化 **MUST**。基準は §2 の配布列を流用し、新規軸を追加 **MUST NOT** |
| **FR-2** | 判定結果の実装は**既存の配置・機構の再利用を優先** **MUST**。**マニフェストを支える検査群・分類学・メタデータ列を新設すること MUST NOT**（マニフェストそのものは FR-3 の必須成果物であり禁止対象ではない / **v1.2 で FR-3 との字義矛盾を解消**）。**具体的な実装手段は design で決定する**（§7 未決 6） |
| **FR-3** | 判定結果は**パッケージング境界**として表現 **MUST**（表現形式は §7 未決 1）。リポジトリを分割すること **MUST NOT**（self-hosting 維持 / §1.4） |
| **FR-4** | 判定対象は **R1 の 15 ファイルに限定する**（**v1.2 で縮小**）。`.claude/skills/` `.claude/agents/` `.claude/hooks/` は **D-1 のスコープ外**とし、後続に送る **MUST**<br>**縮小の理由**: 初版は約 82 ファイル（skills 約 33 / agents 12 / hooks 7 / R1 15）を対象としながら、成功基準は R1 15 件しか検証していなかった（WBS 100% Rule 違反）。かつ **NFR-2**（判定者はユーザー本人）の下で 82 ファイルは完走可能性が低い。**「入れると言って検証しない」状態を解消するため、対象を絞る側に倒した** |
| **FR-5** | 判定結果は**単発の記録**として残す **MUST**。定期再判定の手続を条文化すること **MUST NOT**（WC-11 防御 / §5） |
| **FR-6** | 配布物から除外される資産について、**除外後も self-hosting が成立すること**を確認 **MUST**（開発環境では引き続き全資産が有効であること） |

### 非機能要件

| ID | 要件 |
|:--|:--|
| **NFR-1** | 本 Milestone は §A 常駐指令カウントを増やさない **SHOULD**（増やす場合は誕生ゲートを通す **MUST**） |
| **NFR-2** | 判定作業に L1 / L2 / L3 の**事前採点**を用いること **MUST NOT**（M-1 の自己申告問題の再生産 / HGA #20 D-2）。判定者はユーザー本人 **MUST**<br>**「事前採点」と「証拠収集」の線引き（v1.2 で明文化）**: 許されるのは**結論を出さない情報提示**（パス文字列・個人名・予算数値・外部リポジトリ参照の**検出と提示** / 例: `grep -l "D:/work7"`）。禁じるのは**採否・分類の判断**（「これは配布物である／ない」の下書き、優先度づけ、推奨の付与）。**判定基準自体が §2 で「ほぼ機械判定」とされているため、機械が引ける線までは機械が引き、線を引けない箇所のみをユーザーに提示する**のが正しい分担である |
| **NFR-3** | 成果物に「何が配布物か」の**検査機構**を新設すること **SHOULD NOT**（WC-10 防御 / §5） |

5. **成功基準 3 の解決先** —— 無条件検査を置くのか、置かない判断にするのか
