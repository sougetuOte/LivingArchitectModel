# フェーズ別ガードレール

## PLANNING

### 承認ゲート

```
requirements → [承認] → design → [承認] → tasks → [承認] → BUILDING
```

成果物完成時は必ず「承認」を求める。ユーザーが「承認」と言うまで次へ進まない。

### 承認要求提出直前の体験シミュ (MUST / Fable-Alembic L3)

requirements / design / tasks の各成果物完成時、ユーザーへ承認要求を提出する**直前**に、承認判断をするユーザー本人を受け手として **60 秒実況 3-5 文** を行う (成果物毎 3 発火 / `fable-l3-protocol.md` §5.1)。

- 主語は受け手 / 詰まる・迷う・イラつく瞬間を拾う
- 実況で「なぜこの構成？」「前段の X はどこ？」等の疑問が湧いたら、承認要求本文に理由 1 行を先回りで追記してから提出せよ
- 詰まり仮説 1 行 + 実況第 1 文の**2 行**を承認要求本文の冒頭に残す (テンプレ化ガード / §5.4 ガード 4)
- 書けない場合は宣言中止し、受け手 (依頼者本人か / チームレビュアーか) の特定をユーザーに確認せよ (§5.4 ガード 5 準拠 = 受け手に制約 1 つを必ず付ける / 「フェーズ警告テンプレート」の 3 択には押し込まない = 実況不能は情報不足の信号)

詳細ガード (同型構文検出 / 「詰まる瞬間」検出 3 回連続閾値 / 検知修正 1 文完結禁止) は `fable-l3-protocol.md` §5.4 参照。

### 品質基準

成果物は `.claude/rules/planning-quality-guideline.md` に準拠すること:
- 仕様書: Requirements Smells 検出 + RFC 2119 キーワード統一
- 設計書: Design Doc チェックリスト（非スコープ・代替案・成功基準）
- タスク: SPIDR 分割 + WBS 100% Rule（仕様⇔タスクのトレーサビリティ）
- 明確化: Example Mapping（`/clarify` 併用）

### 禁止

- 実装コード生成（.ts, .py, .go 等）
- `src/` への変更
- 設定ファイル変更（package.json, pyproject.toml 等）
- 未承認での次サブフェーズ開始

### 許可

- `docs/specs/`, `docs/adr/`, `docs/tasks/`, `docs/artifacts/` への出力
- 既存コード読取（仕様策定のため）、Mermaid 図表作成
- `.claude/states/*.json` の更新

## BUILDING

### 必須

- 実装前に `docs/specs/` を確認
- **F0 (4 行アンカー) を実施** — 下記 §F0-F4 埋込 参照
- TDD サイクル厳守（Red → Green → Refactor）
- コード変更時はドキュメント同期
- 1サイクル完了ごとにユーザーに報告

### F0-F4 埋込 (Fable-Alembic L3 / 実行プロトコル準拠)

Task 単位 (`tasks.md` の W7-B4-T9 相当) で F0-F4 を発動する。TDD 1 サイクル毎に F0 生成は儀式過剰のため Task 単位が正 (`fable-l3-protocol.md` §6.1)。

**省略基準**: 3 手未満の自明タスクは F0-F2 を省略可 (F3-F4 は省略不可)。

#### F0 (4 行アンカー / 常時)

「実装前に `docs/specs/` を確認」の直後に発動。以下 4 行を明示:

- 完了条件 (観測可能な形で)
- 検証方法 (実コマンド or 手順 1 つ / 書けなければ理解不足 → Phase 1 = F1 へ)
- やらないこと (スコープ拡大の錨)
- 受け手 (`fable-l3-protocol.md` §5.4 ガード 5 の制約 1 つ必須 = 時間ない / 文脈知らない / 前提 1 個抜け 等)

F0 は AoT 適用でも軽量モードでも常時実施。

#### F1 (事実/仮定/不明の仕分け) — AoT 前段として維持

**AoT Atom Decomposition から除外**する。Atom 分解の 3 条件 (自己完結性 / 契約 / エラー隔離) に F1 対応物なし。F1 を落とすと Atom 入力自体が「事実のふりをした仮定」で汚染される。

依頼文中の名詞 (ファイル名・関数名・「〜のはず」) に仮定タグを付ける。

#### F2 (リスク順分解) — AoT 適用時は Atom Decomposition で置換

- AoT 適用時: Atom Decomposition が F2 の役割を果たす (自己完結性 + 契約 + エラー隔離 + 依存グラフ = リスク順分解と同型)
- 軽量モード (非 AoT): F2 のみ実施 (簡単な部分先に片付ける = 罠)

**F1 と F2 の関係**: F1 は AoT 適用時も維持、F2 のみ AoT で置換される。二重記入 (Atom Decomposition と F2 の両方書き出し) は禁止。

#### F3 (実行ループ / 圧縮 1 問) — TDD サイクル境界で発動

Task 内の TDD Red-Green-Refactor サイクルのイテレーション境界で発動:

- **圧縮 1 問**: 「次の一手は残リスク最大のピースか」
- **独立逃し弁** (圧縮対象外 / 手が止まったら復活): 「人間しか答えられないことで詰まってないか」(規範 §4 例外 2 = 環境起因即報告)

**試行上限** (F3 と連動 / `fable-l3-protocol.md` §6.7 準拠):
- 同一原因・同一アプローチの再試行は 2 回まで
- 合計 3 アプローチまで
- 試行カウントを報告に明示 (「試行 2/3」形式 / 自己都合の数え直し禁止)
- 破壊的操作は試行の弾に数えない
- 環境起因と切り分けた時点で即報告

F4 (全体検証 5 点) は AUDITING フェーズで発動する (下記)。

### AoT/MAGI 適用条件 Self-Check

タスク着手前に以下 3 軸を確認し、いずれか該当時は AoT 分解 + MAGI 合議を実施する:

- [ ] 判断ポイントが 2 つ以上
- [ ] 影響レイヤー/モジュールが 3 つ以上
- [ ] 有効な選択肢が 3 つ以上

該当時は実装着手前に MAGI 合議を完了し、結論を Action として記録すること。
ユーザーから「別の要因が湧きそう」等の指摘を受ける前に自発的に確認する。

根拠: `.claude/rules/decision-making.md` / B-3 retro（2026-06-17 / 2026-06-18）で連続 Try 化。

### TDD 品質チェック

- [ ] R-1: 仕様突合 — FR/設計仕様のフィールド名・定数名と実装が文字単位で一致
- [ ] R-4: テスト網羅 — 各 FR/要件に対応するテストが存在する
- [ ] R-5: テスト名と入力値の一致 — テスト名に含まれる数値・条件と、実際のテスト入力値が一致していること（例: `test_10k_boundary` なら入力は 10,000）
- [ ] R-6: 設計書出力ファイルからのアサーション生成 — 設計書に「ファイル X を生成する」と記載された出力は、Red ステップで `assert path.is_file()` を書くこと

### 仕様同期ルール

- S-1: Green 直後に対応する `docs/specs/` を確認し、実装と仕様の乖離がないか検証
- S-3: 仕様書の未実装項目には Phase/Wave マークを付与（暗黙スキップ禁止）
- S-4: Refactor で公開 API/インターフェースが変わった場合、仕様書を即時更新

### TDD 内省パイプライン v2

PostToolUse hook がテスト結果（JUnit XML）を読み取り、FAIL→PASS 遷移を自動記録する。
`/retro` 実行時に人間がパターン分析を行い、同一パターンが閾値（2回）以上出現する場合にルール候補を提案する。

- パターン記録: `.claude/tdd-patterns.log`（自動、PG級）
- パターン詳細: `docs/artifacts/tdd-patterns/`
- ルール候補: `.claude/rules/auto-generated/draft-*.md`（PM級で起票・承認）
- パターン分析: `/retro` Step 2.5
- 審査コマンド: `/pattern-review`

詳細: `.claude/rules/auto-generated/trust-model.md`

### 禁止

- 仕様書なし実装
- テストなし実装（BUILDING 実行中は絶対禁止 = 作業を止める規律 / AUDITING 時点の重要度判定では `code-quality-guideline.md` §Warning「テストが存在しない新規ロジック」を用いる）
- ドキュメント未更新

## AUDITING

### AUDITING での修正ルール（v4.0.0）

権限等級（`.claude/rules/permission-levels.md`）に基づく修正制御:

- **PG級の修正**: 許可（自動修正可。フォーマット、typo、lint 違反等）
- **SE級の修正**: 許可（修正後に報告。テスト追加、内部リファクタリング等）
- **PM級の修正**: 禁止（指摘のみ、承認ゲート。仕様変更、ルール変更等）

> v3.x からの変更: 従来は「修正の直接実施禁止」だったが、v4.0.0 で PG/SE 級の修正を許可に緩和。

### 必須

- チェックリストに基づく網羅的確認
- 重要度分類: Critical / Warning / Info（判断基準は `.claude/rules/code-quality-guideline.md` に準拠）
- 3 Agents Model 適用、根拠明示
- 問題の PG/SE/PM 分類（権限等級に基づく）

### コード品質チェック

- [ ] 命名が意図を表現している
- [ ] 単一責任原則を守っている
- [ ] エラーケースが網羅されている

### F4 (全体検証 5 点 / Fable-Alembic L3 / 実行プロトコル準拠)

`/auditing` フェーズ開始時に**1 箇所固定**で発動 (`/ship` Phase 5 後の発火は禁止 = commit 済で「壊しに行く」検証が遅く、かつ /ship に儀式 2 個載ると両方形骸化する)。

- [ ] 作った層と別の層で確認する (コード → 実行 / 文章 → 初見の読者として読む = 60 秒実況のコード版)
- [ ] 壊しに行く (空入力・境界値・変な順に当てる)
- [ ] 原因の説明を観測で裏取りする
- [ ] 報告に書く各原因に「症状への寄与の証拠」を 1 つずつ持つ。なければ「寄与は未確認」と書け
- [ ] 「コードが直っていても説明が観測と矛盾していればその報告は嘘だ」

### コード明確性チェック

- [ ] ネストした三項演算子がない
- [ ] 過度に密なワンライナーがない
- [ ] デバッグ・拡張が容易な構造

### ドキュメント・アーキテクチャ

- [ ] 仕様と実装の差異がない
- [ ] ADR 決定事項が反映されている
- [ ] 循環依存がない
- [ ] TODO/FIXME の棚卸し

### 改善提案の禁止事項

- 読みやすさを犠牲にした行数削減
- 有用な抽象化の削除
- 複数の関心事を1関数に統合
- デバッグ困難な「賢い」コード提案
- 主観的な好みに基づく指摘

### Green State 条件

```
Critical = 0 かつ Warning = 0 → Green State（監査通過）
```

Info は件数にかかわらず Green State を阻害しない。
詳細な判断基準は `.claude/rules/code-quality-guideline.md` を参照。

### 監査レポート提出直前の体験シミュ (MUST / Fable-Alembic L3)

監査レポートを提出する**直前**に、レポートを読んで次の修正判断をする作業者 (自分の後続セッション or 別担当) を受け手として **60 秒実況 3-5 文** を行う (`fable-l3-protocol.md` §5.1)。

- 受け手には制約 1 つを必ず付ける (§5.4 ガード 5 / 例: 「Critical 何件かだけ知りたい PM」「該当ファイルを開いて直す作業者」)
- 実況で「Critical と Warning のどちらから手を付ければ？」「この Info は無視して良いのか？」で詰まる瞬間があれば、レポート冒頭に優先順位 1 行を追加せよ
- 詰まり仮説 1 行 + 実況第 1 文の**2 行**を「総合評価」行の直上に残す (テンプレ化ガード / §5.4 ガード 4)
- 書けない場合は宣言中止 (実況不能は情報不足の信号 / フェーズ警告 3 択には押し込まない)

詳細ガード (同型構文検出 / 「詰まる瞬間」検出 3 回連続閾値) は `fable-l3-protocol.md` §5.4 参照。

### レポート形式

```
# 監査レポート
対象: [ファイル/ディレクトリ]
Critical: X件 / Warning: X件 / Info: X件
総合評価: [A/B/C/D]
```

## フェーズ警告テンプレート

フェーズルールに反する要求を受けた場合:

```
⚠️ フェーズ警告: 現在は [PHASE] フェーズです。
1. ルールに沿って続行
2. フェーズ切替（/planning, /building, /auditing）
3. 「承知の上で続行」と明示
```
