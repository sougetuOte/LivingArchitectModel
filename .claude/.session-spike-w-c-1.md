**gabriel.md 実装方針**:

LAM 基盤（Claude Code の Agent/Task ツール）には subagent 実行を打ち切る timeout パラメータが
存在しない。したがって **呼び出し元（gabriel を呼び出す MAGI フロー側 / `.claude/skills/magi/SKILL.md`
実装、または `.claude/skills/magi/` 配下の python 実装があればそちら）で経過時間を自前計測する**
方式を採用する。

実装パターン（呼び出し元計測、擬似コード）:

```python
import time

GABRIEL_TIMEOUT_SEC = 60  # NFR-W-C-1 SHOULD 60秒以内

start = time.monotonic()
try:
    result = invoke_gabriel_subagent(stub_conclusion)  # Agent(Task) tool 呼び出し相当
    elapsed = time.monotonic() - start
    if elapsed > GABRIEL_TIMEOUT_SEC:
        # NFR-W-C-1 は SHOULD（MUST ではない）: 超過時は verdict=inconclusive 相当として扱う
        # design.md §5 の timeout 経路（inconclusive 同等）にフォールバック
        result = {"verdict": "inconclusive", "reasoning": "timeout exceeded", ...}
except AgentInvocationError:
    # Agent ツール自体は同期呼び出しであり、呼び出し元スレッドをブロックする形で完了を待つ。
    # Claude Code 側に「N秒で強制中断する」API がないため、実質的には
    # 「呼び出し元が明示的にキャンセルする」手段も存在しない（一度呼んだら完了を待つしかない）。
    # → 60秒制限は「検出（ログに記録し inconclusive 扱いに倒す）」のみ可能で、
    #   「強制中断」は LAM 基盤側では実現不可能というのが本 Spike の重要な副次的発見
    ...
```

Anthropic 公式の timeout 制御手段（具体化）:

- `command` / `http` / `mcp_tool` / `prompt` / `agent` タイプの **hooks** には `timeout`
  フィールドが settings.json 上に存在する（例: PreToolUse hook の JSON 設定に
  `"timeout": 30` を指定可能）。ただしこれは **hook スクリプト自体**（例:
  `.claude/hooks/pre-tool-use.py`）の実行時間上限であり、hook が監視する
  「Agent ツール呼び出し全体」の時間とは別物。gabriel 実行そのものを打ち切る用途には使えない。
- Bash ツールには `timeout`（ミリ秒、最大 600000）という明示パラメータがあるが、
  Agent（Task）ツールには同等のパラメータが **存在しない**（本セッションのツールスキーマ・
  実ログ両面で確認）。

結論として、gabriel.md 自体（subagent 定義ファイル）に timeout 設定を書き込む余地は
Claude Code の公式仕様上ない。実装は次の 2 点に集約される:

1. gabriel を呼び出す MAGI フロー側コード（Sonnet L2 が Stage 3 WC-B5-T5/T6 で実装）で、
   Agent 呼び出し前後に `time.monotonic()`（または同等）で時刻を取得し、経過時間を記録する
2. 60 秒（NFR-W-C-1 は **SHOULD**）を超えた場合は「検出してログに残し、
   design.md §5 の timeout 経路（verdict=inconclusive 同等の扱い）にフォールバックする」
   運用とする。Claude Code 基盤側に「強制中断（cancel/abort）」API がないため、
   「呼び出し自体を N 秒で強制終了する」実装は不可能。実質的には
   「終わったあとに経過時間が超過していたかどうかを判定し、事後的に inconclusive 扱いに倒す」
   というソフトな検出に留まる（NFR-W-C-1 が MUST ではなく SHOULD である設計上の理由と整合的）

**未解決 / 要検証の仮定**:

- `settings.json` の他セクションや Claude Code の環境変数専用ドキュメント
  （本 Spike では WebFetch していない `/en/settings` 以外のページ、例えば
  CLI リファレンスや `/en/environment-variables` 相当のページ）に、Bash 以外のツール
  （Agent 含む）向けの timeout 系環境変数が存在する可能性は完全には排除できていない
  （**要検証の仮定**）。ただし `/en/hooks` と `/en/settings` の直接 WebFetch では
  Agent/Task 専用の timeout 設定は確認できなかった
- gabriel.md 自体は本 Spike のタスク境界（`.claude/agents/` 配下への新規作成禁止）により
  未作成のため、実際に gabriel.md 形式の subagent を 30 秒制限で動かして
  タイムアウト挙動を直接観測するテスト（tasks.md WC-B5-T1 完了条件の「30 秒制限テストで
  timeout 挙動を観測」）は本 Spike では実施していない。上記の結論は
  公式ドキュメントの記述 + 既存 jsonl ログのフィールド不在の確認から導いた
  **設計上の推論**であり、実機での「実際に 30 秒以上かかる subagent が強制終了されるか」
  という直接観測は BUILDING フェーズ（またはこの Spike の追試）で行うことを推奨する
- 「呼び出し元が同期的に待つ以外に手段がない」という記述は、Claude Code の Agent ツールが
  非同期キャンセル API を外部に公開していないことの傍証（tool schema にキャンセル関連
  パラメータが存在しない）に基づくが、内部実装（サーバー側のタイムアウト強制の有無）
  そのものを直接検証したわけではない（**要検証の仮定**: Claude Code サーバー側に
  非公開のグローバル timeout が存在し、それに達すると Anthropic 側から強制終了される
  可能性はゼロではない。ただし公開仕様としては呼び出し元に制御手段がない、という点は確定）

## T2: OQ-W-C-1 独立コンテキスト検証

**結論**: 部分分離

**根拠**:
- 公式 doc 記述: https://code.claude.com/docs/en/sub-agents （「Manage subagent context」§「What loads at startup」）
  > "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there."
  > "A non-fork subagent's initial context contains: **System prompt**: the agent's own prompt plus environment details that Claude Code appends, not the full Claude Code system prompt... **CLAUDE.md and memory**: every level of the memory hierarchy the main conversation loads, including `~/.claude/CLAUDE.md`, project rules, `CLAUDE.local.md`, and managed policy files. The built-in Explore and Plan agents skip this. **Git status**: a snapshot taken at the start of the parent session."
  → 公式ドキュメントは明確に「会話履歴は分離されるが、CLAUDE.md 階層は Explore/Plan を除く全 subagent（custom subagent 含む）にロードされる」と記述している。gabriel のような custom agent は対象外にはならない。
- LAM 既存 subagent 実測:
  - 分析対象 jsonl（実読）:
    - `C:\Users\metral\.claude\projects\D--work7-LivingArchitectModel\cdfee686-90db-4226-b2db-f58f8f43c337\subagents\agent-a1665ce647e338edd.jsonl`（TEST-B 監査タスク、v2.1.170、2026-06-10）
    - `C:\Users\metral\.claude\projects\D--work7-LivingArchitectModel\64fb6e40-01ec-464e-b81d-3f62c043f109\subagents\agent-a4f1779f4b1b03513.jsonl`（goal-driven-orchestration W1-T2、v2.1.170、2026-06-12）
  - user prompt (line 1) の内容確認: 両ファイルとも line 1 の `message.content` は **Task ツールの委譲プロンプト文字列のみ**。親セッションの会話履歴・過去ターンのテキストは一切含まれない（`parentUuid: null`, `isSidechain: true`）。ただし委譲プロンプト自体は L1（親）が手動で必読ファイル（仕様書パス等）を書き込んでおり、親の「判断結果」の要約という形で間接的にコンテキストが渡される設計になっている（プロンプト内に「design.md に書かれていない数値を発明しないこと」等の独立検証を促す指示も L1 側で明記されていた）
  - system prompt の継承挙動: 両ファイルとも `grep '"type":"system"'` = 0 件（`user`/`assistant`/`direct`/`message` のみ存在）。CLAUDE.md 本文（「PROJECT CONSTITUTION」「Living Architect」等のリテラル文字列）を transcript 全体に grep しても 0 件ヒット。→ **CLAUDE.md は transcript の `user`/`assistant` メッセージとしては記録されておらず、API 呼び出し時の system プロンプトパラメータとして別途注入されている**（transcript ファイルに残らない）ことが確認された。これは公式 doc の「system prompt: 分離 (own prompt + env details)」という記述、および「CLAUDE.md は memory hierarchy として別途ロードされる」という記述と整合する（transcript のフォーマットが system プロンプト全文を保存しない設計と考えられる）
- 分離度の証拠:
  - `parentUuid: null` — 両ファイルで一致。subagent の最初のメッセージは親 transcript の特定 UUID にチェーンしていない（完全に独立した新規スレッドとして開始）
  - `isSidechain: true` — 両ファイルで一致。sidechain フラグにより、subagent の会話が main と別系列であることが明示されている
  - `sessionId` — subagent 側 jsonl 内の `sessionId` は親セッションの `sessionId` と同一値が入る（例: `cdfee686-90db-4226-b2db-f58f8f43c337`, `64fb6e40-01ec-464e-b81d-3f62c043f109`）。つまり subagent は独自の `sessionId` を持たず、親セッション ID の下にぶら下がる形（ファイルパスも `<parent-session-id>/subagents/agent-<agentId>.jsonl`）
  - `agentId` — subagent 固有の識別子（例: `a1665ce647e338edd`, `a4f1779f4b1b03513`）。公式 doc の「Resume subagents」節にも `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` という同一パス構造の記述があり、実ファイルと一致することを確認
  - Git status: 公式 doc は「a snapshot taken at the start of the parent session」と明記。親セッション開始時点のスナップショットが渡るため、subagent 起動時点ではなく親セッション開始時点の状態が渡る（今回の 2 ファイルでは transcript 内に明示的な git status 注入テキストは見当たらなかったが、system プロンプト同様 transcript に残らない可能性が高い — 要検証）

**gabriel.md 実装含意**:
- gabriel は MAGI（M/B/C も全て Opus の別ペルソナ）の結論を評価する adversarial agent だが、公式仕様上「CLAUDE.md 階層は subagent にも通常通りロードされる」ため、**LAM の思想的枠組み（Hierarchy of Truth, MAGI System 定義, decision-making.md 等）自体は gabriel にも継承される**。これは bias 源にはならない（むしろ gabriel が LAM のルールを知らないと審査基準が食い違う）
- 真のリスクは「会話履歴」ではなく「委譲プロンプトの書き方」にある。実測した 2 例では、L1 が委譲プロンプト内に **判断の結論や前提を要約して書き込む**ため、L1 が誤った前提を持っていた場合、その誤りごと gabriel に渡ってしまう構造的リスクがある（transcript の会話履歴は分離されていても、L1 が手で書く「委譲メッセージ」経由でバイアスが漏れる余地は残る）
- 独立コンテキスト前提だけでは不十分。追加防御が必要:
  - gabriel.md の system prompt に「MAGI の結論（M/B/C の合意事項）をそのまま正としない。結論に至った**前提・根拠・棄却された代替案**を独立に再検証せよ」という明示的指示を入れるべき（「結論の是非」でなく「結論に至るロジックの妥当性」を審査対象にする）
  - 委譲プロンプトの設計時、L1 は「MAGI がこう結論した、これを承認せよ」という書き方を避け、「MAGI の Divergence/Debate/Convergence の生ログ（または要約）と、争点になった判断ポイントを提示する。結論への賛否は書かない」という中立的な委譲プロンプト設計にすべき（`hga-summoning.md` の「ブリーフに結論を先に書かない」規律と同型の防御パターンが使える）
  - MAGI 自体が単一モデル（Opus）の別ペルソナであるため盲点が相関する、という `hga-summoning.md` の既存知見（「MAGI の split は非対称シグナル」）はそのまま gabriel にも適用可能。gabriel も同一系列モデルなら同じ盲点を継承しうるため、model 選定（別モデル系列を使うか等）を design 時に検討する価値がある
